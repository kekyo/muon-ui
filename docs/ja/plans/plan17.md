# Android・PC共通のバックグラウンドサービス

## 目的と対象

開発者がmuonのページとは独立して動作するサービスを実装できるようにする。AndroidとCEFを使うPC版で、サービスの定義、寿命の管理、ページとの通信、SDKを可能な限り共通化する。PC版の対象は現在の配布対象であるLinuxとWindowsとする。

まずC/C++でサービスを実装できるようにし、ページのJS/TSとの双方向通信を追加する。その後、QuickJSで実行するJS/TSサービスと、そこから開発者のネイティブコードを呼び出す仕組みを提供する。C/C++による実装方法は維持する。PC版では既存のNode.jsサイドカーを利用したサービスも検討し、実現できる場合は共通の通信APIへ接続する。

UIとサービスは別々の寿命を持つ。PC版では、すべてのウィンドウを閉じてCEF側のプロセスが終了しても、常駐を指定したサービスは動作を続ける。ユーザーセッションの開始時にUIを表示せずサービスだけを起動できるようにする。アプリ全体の明示終了とユーザーセッションの終了は、サービスを含む終了契機とする。AndroidではOSの起動・継続制限に従い、同じAPIでも常時動作を保証しない。

本計画は2026年11月12日までの設計議論と、現在のコードベースに基づく。API名や設定キーの例は設計案であり、実装済みの公開機能を示すものではない。各段階で型定義と動作を確定する際も、以下の寿命と設定の意味を維持する。

## 現在の構成と再利用する部分

| CEF | [muon_client.cpp](../../../core/cef/src/browser/muon_client.cpp)で最後のbrowser終了時にランタイムを停止し、メッセージループを終了する | UIの終了からサービスの停止を切り離す |
| Node.js | [node_plugin.cpp](../../../node/native/node_plugin.cpp)と[node/src/index.ts](../../../node/src/index.ts)に別プロセスの起動とRPCがある | プロセスの所有者をページからサービスホストへ移す |

| Android公開ビルド | [ui/android/target.ts](../../../ui/android/target.ts)ではQuickJSを公開対象としていない | サービス用の設定検証、資材生成、配布を段階的に追加する |

共通ランタイムにはプロセス内で共有するhelperへの参照があるため、同一プロセスに独立したプラグインランタイムを無条件に複数作らない。初期構成は1プロセスにつき1つのプラグインランタイムとし、その下で複数の論理サービスを管理する。ライブラリーのロード時初期化と、サービスごとの状態の生成・破棄は区別する。

AndroidのQuickJS PoCはActivityからのbindと破棄に結び付いている。別プロセスにあることだけではUIから独立した常駐にはならない。また、JNI、POSIXソケット、実行ループが同じ実装に含まれているため、そのままWindowsへ移植せず、エンジンとOSアダプターを分ける。

## サービスの定義とホスト

### 論理サービスと実行環境

サービスはアプリ内で一意なIDを持つ。同一アプリ・同一利用者の実行環境で、1つのIDにつき1つの稼働インスタンスを管理する。設定をプロファイル別に分ける場合は、その区別もホストの識別に含める。複数のIDを最初の段階から扱い、サービスAの参照や自動起動設定をサービスBと共有しない。

サービスホストは設定、参照、実行状態、通信先を管理する。ページはホストのクライアントとなる。サービスID、実行世代、ページセッションID、参照IDを区別する。実行世代は停止後の再起動やプロセス再生成を識別する値で、古い実行結果を新しいインスタンスへ渡さないために使う。

サービスの数とプロセスの数は別に扱う。同じプロセスへ配置したサービスは、プロセスの異常終了や強制終了の影響を共有する。初期版でサービスごとの障害分離を一律に保証しない。配置の都合をページ側の通信APIへ露出させない。

### muon.jsonと利用者設定

`muon.json`の`services`にはビルドするサービスの一覧を記述する。実行時APIはこの一覧にあるサービスを取得・設定する。任意のファイルを実行時にサービスとして登録する機能は初期範囲に含めない。

| 定義する情報 | 内容 |
| --- | --- |
| サービスID | ページと設定から参照する名前 |
| 実装方式 | native、QuickJS、PC用Node.js |
| 実装資材 | nativeの成果物、またはJS/TSのエントリーとビルド対象 |
| 公開インターフェイス | メソッド、引数、戻り値、エラー、購読イベントの定義 |
| 自動起動の既定値 | 利用者による上書きがない場合に使うON/OFF |
| プラットフォーム設定 | Androidのforeground serviceの用途・権限・通知など |

利用者の変更はアプリの永続設定へ保存し、配布済みの`muon.json`は書き換えない。有効な自動起動設定は「利用者の上書き、なければ`muon.json`の既定値」の順で決める。参照数やページの参照IDは保存しない。

UIの自動表示とサービスの自動起動は別の設定とする。既存の`environments.getAutostart()`・`setAutostart()`はUIの起動設定を表すAPIとして整理する。OSへの起動登録が存在するかどうかだけで、UIのスイッチ状態を返さない。

## 参照による寿命の管理

### 所有者と生存数

公開APIの基本操作はサービスの取得と参照の解放とする。共有サービスを直接開始・停止する`services.start()`・`stop()`は基本操作にしない。

サービスごとの生存数は次の参照から求める。

```text
N = H + C
H: ホストが持つ常駐参照。0または1。
C: ページなどの利用者が持つ参照。起動待ちの取得予約も含む。
```

ホストは所有者と一意な参照IDの集合を管理し、その件数から生存数を求める。ページへ生のカウンタ操作を公開しない。有効な自動起動設定がONならホストの常駐参照を1つ持つ。OFFなら常駐参照を持たず、利用者の取得に応じてサービスを動かす。

`acquire(id)`は起動処理を待つ前に参照を予約し、利用可能になった時点でハンドルを返す。複数ページが同時取得しても起動は1回とする。取得に失敗した場合は予約を取り消す。JSの変数へ同じハンドルを代入しても、新しい参照は増やさない。

`release()`はそのハンドルが所有する参照だけを解放する。同じハンドルへの重複実行は無害とする。ページ破棄、ナビゲーション、UIプロセス終了、IPC切断では、そのページセッションが持つ参照と取得予約をホストが回収する。JSの終了イベントやGCだけには依存しない。

状態の照会や購読は生存参照を取得しない。管理画面を開いたために停止待ちのサービスが生存し続けることを防ぐ。サービスのメソッドを呼び出す場合は参照を取得し、必要な処理が終わるまで保持する。

### 起動・停止の状態

生存数が1以上であることは実行を必要とする状態を示す。OSが実際にプロセスを動かしていることは、`stopped`、`starting`、`running`、`stopping`、`failed`などの実行状態で別に表す。

| 状況 | 動作 |
| --- | --- |
| 停止済みのサービスに最初の参照を取得 | 参照を予約して起動する |
| 起動中に別のページが取得 | 同じ起動完了を待つ |
| 起動待ちのページが消滅 | そのページの予約だけを取り消す |
| 生存数が0になる | 新しい処理の受付を止め、非同期の停止処理へ進む |
| 停止が確定した後に新しい取得が来る | 古い世代の停止を完了させ、参照が残っていれば新しい世代を起動する |
| 古い世代の応答・コールバックが届く | 新しい世代には配送しない |
| 起動失敗・サービスの異常終了 | 待機中の取得や要求を失敗させ、理由と実行状態を通知する |
| OS制限・アプリ全体の明示終了 | 生存数に関係なく終了させ、通知できる場合は利用者へ終了理由を伝える |

実行世代の終了時はその世代で発行済みのハンドルを無効にし、対応する利用者参照を回収する。常駐参照と、停止後の次世代を待つ取得予約は区別して扱う。古いハンドルで新しい世代を操作できないようにし、再利用には新たな取得を必要とする。無効になったハンドルの`release()`は無害とする。アプリ全体が強制停止されて通知できなかった場合は、次回起動時にOSから取得できる終了理由を提示する。

停止時は実行中の要求を完了させるか取り消すかを共通規約で定め、停止完了前に必要なdispatcher、コールバック、ライブラリーを破棄しない。AndroidのOS期限がある終了では、その期限を優先する。停止処理が応答しない場合の強制終了は、同じプロセスの他サービスにも影響するため通常の参照解放とは区別する。

初期版は生存数が正であるという理由だけで、失敗後の再起動を繰り返さない。再取得などの明示的な契機で再試行する。将来自動再起動を追加する場合は、回数や待機、OSによる停止との区別を独立した方針として定義する。

アプリ全体の終了時はその終了処理中に自動起動設定から常駐参照を再生成しない。永続設定は維持し、次の正規のアプリ起動やユーザーセッション開始で評価する。サービスの終了だけで、開いているUIを終了させない。

ページを閉じた後も続ける仕事には、常駐参照などページ以外の所有者が必要になる。初期版で暗黙の自己参照や永続ジョブを追加しない。将来サービス間の参照を認める場合は、循環参照を許可しない構成から始める。依存関係全体の自動管理は別の拡張とする。

## 自動起動スイッチと現在の動作

### ON/OFFの意味

UIの「サービスを自動的に起動させる」スイッチは、永続設定と現在の常駐参照を同時に変更する。API案は`muon.services.setAutostart(id, enabled)`とする。この管理操作のために対象サービスを取得する必要はない。

| 操作 | 永続設定 | 現在の常駐参照 | ページの参照 |
| --- | --- | --- | --- |
| ON | ONを保存 | 存在しなければ1つ追加 | 変更しない |
| 再度ON | ONを維持 | 1つのまま | 変更しない |
| OFF | OFFを保存 | 存在すればその1つだけ解放 | 変更しない |
| 再度OFF | OFFを維持 | 0のまま | 変更しない |

OFF後もページが利用していればサービスは動き続け、最後の参照が解放された時点で停止する。OFFは明示的な`acquire()`を禁止する設定ではない。後から別のページが取得すれば、その参照がある間だけ起動できる。

`muon.json`の既定値がOFFでも、利用者がONにすれば常駐参照を持つ。既定値がONでも、利用者がOFFにした後のホスト再生成で勝手にONへ戻さない。判断には静的な設定だけでなく、有効な利用者設定を使う。

複数ページからの設定変更はホストで順序付けし、設定の改訂番号を通知する。同じ値の繰り返しは参照数を変えない。ON→OFF→ONの途中で古い起動・停止処理が完了しても、最新の設定を上書きしない。設定保存に失敗した場合は成功として返さず、公開状態と保存済み状態を一致させる。

管理APIの完了は、設定の保存と常駐参照の変更が完了したことを表す。サービスの起動完了・停止完了とは分ける。呼び出し元がページ参照を持ったままOFFの完了を待っても、相互に待ち合う状態を作らない。

停止完了を待つ必要がある場合は、参照を増やさない状態通知を使う。特定の停止を待つ操作は実行世代を指定し、その直後に別の利用者が再起動しても、古い世代の停止を観測できるようにする。

### UIに表示する状態

管理UIは設定と実行状態を分けて表示する。たとえば「OFF・ほかのページで利用中」「OFF・停止処理中」「ON・起動失敗」を区別する。ONでも起動がOSに拒否された場合は、設定を保持した上で実行できない理由を示す。状態変更の通知は実行中のサービスを取得せず受け取れるようにする。

スイッチのOFF操作で他ページの参照を破棄したり、プロセスを強制終了したりしない。ユーザーがサービスを止める通常の操作は、この設定変更による常駐参照の解放とする。

### 検討した別案

「カウンタを余分に1減らす」という実装は、常駐参照を識別して解放する操作に置き換える。生の減算では重複要求や、既にOFFになった後の操作を区別できないためである。

設定をONのまま一時的に常駐参照だけ解放する`requestShutdown()`は初期APIに含めない。設定を再評価すると再取得されるため、実現にはセッション内の休止状態が別途必要になる。将来必要になった場合は、その休止の有効期間と解除条件を独立して設計する。

「自動起動設定は次回起動時だけ有効」とする案では、今回のスイッチで現在の動作を変えられない。初期仕様は現在の常駐参照にも即時反映する。

新規取得を拒否して停止へ向かわせる方式や強制終了は、通常のOFFとは異なる管理操作になる。既存の参照が残る限り新規取得を拒否するだけでは停止時刻を保証できないため、初期範囲には加えない。

## プラットフォームごとの実行

### PCのサービスホストとログイン起動

CEFを初期化せずに動作するサービスホストを用意し、UIはIPC経由で接続する。ウィンドウを閉じた後もサービスホストを残せるようにし、UIを開き直すと同じホストとサービスへ接続する。UIを表示しないログイン起動も同じホストを使う。

既存のCEF起動処理は初期browserの生成を前提としているため、単にウィンドウを非表示にする方法には依存しない。サービスホストの単一起動判定と接続先の識別を、CEF側の単一起動処理から独立させる。同時起動してもホストや常駐参照を重複させない。

LinuxではXDG Autostart、Windowsでは利用者のRunキーを使う既存実装を拡張する。OSに登録する起動コマンドはアプリ単位で集約し、その起動処理でUIの自動表示と各サービスの設定を評価する。UIがOFFでもサービスがONなら起動登録を維持し、いずれも不要なら解除する。配布・初回設定で起動コマンドを登録する処理も用意する。[XDG Autostart仕様](https://specifications.freedesktop.org/autostart/latest/)、[WindowsのRunキー](https://learn.microsoft.com/en-us/windows/win32/setupapi/run-and-runonce-registry-keys)

対象は利用者のログインセッション内の常駐であり、OS全体のdaemonやWindows Serviceとしての動作は含めない。通常のランチャーからUIを再表示できることを必須とする。既存のトレイ機能はページに結び付いているため、常駐中の管理をトレイへ追加する場合はホスト所有の機能として分ける。

Node.jsの子プロセスもサービスホストが所有する。現在のrenderer破棄時の終了や、Windowsでの所有プロセス終了に連動した終了処理をそのまま使うとUI終了で停止するため、所有先を変更する。

### Android Service

Activityとは独立したstarted serviceを起動し、継続動作が必要な用途ではforeground serviceとして動かす。Activityからのbindだけで寿命を決めない。UIプロセスとサービスプロセスを分け、UIの終了や再生成後もサービスへ接続できる構成を基本とする。[bound serviceの寿命](https://developer.android.com/develop/background-work/services/bound-services)

複数の論理サービスにはそれぞれの用途、通知、停止を管理できるAndroid Serviceコンポーネントを割り当てる構成を第一候補とする。必要に応じてプロセスを共有できるようにし、Androidコンポーネントと論理サービスの対応を管理する。型ごとの時間枠はアプリ内で共有される場合があるため、コンポーネント分割でOS制限を回避できるとは扱わない。

用途に対応するforeground service type、権限、通知をビルド設定から生成する。任意の処理を無制限に常駐させる汎用typeは設けない。ネイティブライブラリーのロードやJSの評価が遅くても、foreground化を遅らせず、Androidのメインスレッドをブロックしない。[foreground serviceの種類](https://developer.android.com/develop/background-work/services/fgs/service-types)

バックグラウンドからの起動が許可されない場合は、設定のONと実行失敗を区別して通知する。起動機会を待つことと、実際に起動済みであることを同じ成功状態にしない。端末起動時の動作も用途とOSの制限に従い、PCのログイン起動と同じ保証にはしない。[バックグラウンドからの起動制限](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start)

`POST_NOTIFICATIONS`を拒否されたことだけを理由にforeground serviceの起動を禁止しない。通知権限とforeground serviceの起動条件を区別し、サービス側は必要な通知を提供する。[通知権限とforeground service](https://developer.android.com/develop/ui/compose/notifications/notification-permission)

Android 15以降を対象とするアプリでは、バックグラウンドの`dataSync`と`mediaProcessing`にそれぞれ24時間中6時間の制限があり、`shortService`にはさらに短い制限がある。OSのタイムアウト時は通常の参照数より停止期限を優先する。常駐設定がONであっても、停止直後の再起動で制限を回避しようとしない。[foreground serviceの時間制限](https://developer.android.com/develop/background-work/services/fgs/timeout)

OSや利用者によるアプリ全体の停止では、正常終了コールバックを受け取れない場合がある。復旧に必要な状態は処理の区切りで保存し、終了処理だけに依存させない。Activityの終了とアプリ全体の停止をAPI・テストの両方で区別する。[利用者によるforeground service実行アプリの停止](https://developer.android.com/develop/background-work/services/fgs/handle-user-stopping)

## 共通APIと実装方式

### ページとの通信

ページは取得したサービスハンドルを通じてメソッドを呼び出し、サービスは結果、呼び出し中のコールバック、明示的なイベント購読を通じてページへ通知する。native、QuickJS、Node.jsでページ側の使い方をそろえる。

公開インターフェイスには実行時にも利用できる定義を用意する。現在の成果物にある関数パス一覧を拡張し、型、エラー、キャンセル、イベントを記述する。TSのinterfaceだけでは実行時に残らないため、定義からTS型とnative用の記述情報を生成する方式を検討する。

既存RPCの値表現を調べ、文字列、数値、64bit整数、バイナリー、配列などの共通範囲を定める。プロセスをまたぐ生ポインターは公開しない。必要なリソースは所有者と寿命を持つ不透明なハンドルとして表現する。呼び出しの識別、利用可能なメソッドの制限、エラーの種類、切断時の失敗を共通化する。

現在のNode.jsとQuickJSの呼び出しに付随するコールバックは、呼び出し完了時の解放を前提としている。長期間の通知は別の購読として登録・解除し、ページ破棄時はそのページの購読だけを回収する。サービスが再起動した場合は世代の変化を通知し、状態の再取得と購読の再登録を可能にする。副作用のある要求を再接続時に自動再送しない。

### C/C++サービス

サービスSDKは共通のC ABIを公開し、C++からも利用できるようにする。開始、非同期停止、要求の処理、通知の送信、サービスごとの状態を扱う。公開APIへJNI、CEF、QuickJSの`JSValue`などを含めない。

共通のサービス実装ソースをAndroidとPC向けにビルドできることを目指す。OS機能に依存するコードはアダプターへ分け、CPUやOSの違うバイナリーの互換性は求めない。I/Oと非同期処理には既存のcardioを利用し、待機のためだけのスレッドやポーリングを増やさない。

### QuickJSサービス

TS用SDKとViteによるビルド経路を用意し、サービスホストが実行時にJSを読み込む。ページ用SDKとは実行環境を分け、DOMやページの存在を前提にしない。サービスの登録、公開メソッド、イベント、停止時の非同期処理を共通SDKで提供する。

QuickJSランタイムの操作は所有する実行ループへ集約する。PoCからエンジン、モジュール解決、非同期処理を取り出し、AndroidとPCのOSアダプターへ接続する。最初からNode.jsの組み込みモジュール全体との互換性を目標にしない。配布資材はJSを基本とし、QuickJSのバージョンに依存するバイトコードを汎用の配布形式として扱わない。[QuickJS公式文書](https://bellard.org/quickjs/quickjs.html)

### QuickJSからのネイティブ呼び出し

QuickJSにはC関数やCモジュールを登録する埋め込みAPIがある。これを使い、muonの型記述、既存のtra-ffic・libffiによる呼び出し、所有者管理へ接続する。開発者はmuonのネイティブSDKで公開した関数を、QuickJSサービスから呼び出せるようにする。[QuickJSのC API](https://bellard.org/quickjs/quickjs.html)、[公開ヘッダー](https://github.com/bellard/quickjs/blob/master/quickjs.h)

任意のCライブラリーには必要なラッパーと型定義を開発者が用意する。生ポインターの直接操作や、任意の共有ライブラリーを無制限に読み込む汎用FFIは初期範囲に含めない。QuickJS専用Cモジュールを直接作る方法はエンジンABIへ依存するため、共通SDKの標準経路にはしない。

### PCのNode.jsサービス

既存の別プロセス起動とIPCを再利用する。Node.jsのエントリーは共通サービスSDKへ実装を登録し、ページからはQuickJSと同じインターフェイスで呼び出せるようにする。Node.js固有パッケージを使うコードはPC専用となり、Androidでもそのまま動くとは扱わない。

現行の停止応答と`process.exit()`だけでは開発者の非同期終了処理を待てない。サービスの停止要求、処理終了、応答、プロセス終了の規約を追加する。`exit`イベントで非同期の後片付けを完了させる設計にはしない。[Node.jsのexitイベント](https://nodejs.org/api/process.html#event-exit)

共通ネイティブ機能は必要ならサービスホストへのRPCを通じて提供する。Node-APIによる同一プロセスのアダプターや、ネイティブアドオンの全対象向けビルドは初期範囲に含めない。Node.js対応の複雑さが共通APIや寿命の規約を損なう場合は、この段階を独立して保留し、nativeとQuickJSの提供を妨げない。

## 実装段階と完了条件

各段階で先に公開動作を検証するテストを追加し、未実装または問題のある状態で失敗することを確認してから実装する。段階ごとに動作するドライバーを用意し、関連テストを通して適切な粒度でコミットする。公開APIを使う際は公式文書とAPIコメントの両方を確認する。外部コードは変更しない。

### 段階1：共通の参照管理と実行状態

1. `core/common`へサービスID、所有者、参照ID、実行世代、設定の改訂番号を扱う管理部分を追加する。
2. `acquire`、重複解放、所有者の切断、常駐参照のON/OFF、起動・停止中の競合を`core/common-test`で検証する。設定の優先順位と保存失敗も検証する。
3. 開始と停止を任意の時点で完了できるnativeのドライバーを作り、複数サービスの動作と競合を観測できるようにする。

完了条件はOSやCEFなしでドライバーを実行でき、参照の重複解放や過剰取得がなく、古い非同期完了が新しい世代や設定を変更しないことである。

### 段階2：nativeサービスとUIから独立したホスト

1. C ABIのサービスライフサイクルとビルド資材を追加し、同じC/C++ソースからAndroid・Linux・Windows向けにビルドする。
2. PCの独立ホストとAndroidのstarted foreground serviceを実装する。UIの取得・解放とプロセス切断を共通管理へ接続する。
3. `muon.json`で複数サービスと自動起動の既定値を指定できる最小構成を公開する。UIを閉じても仕事を続けるnativeサンプルを用意する。
4. Androidでは外部の観測用APK、PCでは別プロセスのドライバーから、UI終了後の実処理と再接続を確認する。

完了条件は各OSでnativeサービスをビルド・起動でき、常駐参照を持つサービスがUI終了後も処理を完了し、常駐参照のないサービスが最後の参照解放で停止することである。サービスが終了しても開いているUIは利用できることを確認する。

### 段階3：自動起動設定と管理UI

1. サービスの`setAutostart`、設定照会、参照を増やさない状態通知を実装する。利用者設定を保存し、複数ページで同じ状態を観測できるようにする。
2. ON/OFFスイッチを持つ管理サンプルを用意し、OFF後も他ページの利用を継続できること、最後の解放で停止することを検証する。
3. PCのUI自動表示とサービス自動起動を分け、ログイン時の起動コマンドとUIを開き直す経路を実装する。
4. Androidの起動拒否、通知、OSによる停止を状態表示へ反映する。設定変更直後のプロセス再生成でも設定が復元されることを検証する。

完了条件はスイッチを現在と次回の動作へ反映でき、ONの重複で参照が増えず、OFFで他ページを中断しないことである。PCではUIを表示しないログイン起動と再表示を確認し、UIの自動起動OFFがサービスの起動登録を解除しないことを確認する。

### 段階4：nativeサービスとの双方向通信

1. 実行時のインターフェイス定義、TS型、native用記述情報、ページのサービスハンドルを追加する。
2. メソッド呼び出し、結果、キャンセル、呼び出し中のコールバック、長期購読、切断時の失敗を共通化する。
3. 複数ページから同じnativeサービスへ要求を送り、一方のページだけを閉じても他方の要求と通知が継続するサンプルを動かす。

完了条件はAndroidとPCで同じ通信テストが成功し、ページや世代をまたいだ誤配送と、破棄済みコールバックへの呼び出しがないことである。

### 段階5：QuickJSサービスとTS用SDK

1. Android PoCのQuickJS部分を共通エンジンとOSアダプターへ分け、サービスの所有者と非同期停止へ接続する。
2. TS用SDK、JS資材のビルド、読み込み、必要な標準機能を実装する。公開AndroidビルドでQuickJSサービスを指定できるようにする。
3. 段階4と同じインターフェイスのサービスをTSで作り、Android・Linux・Windowsで実行する。nativeとQuickJSのサービスを同時に管理する。
4. PoCにある必要な回帰試験を製品側へ移し、残るPoCの役割と重複を整理する。

完了条件は共通TSソースを両プラットフォームでビルド・実行でき、nativeと同じ寿命・通信テストが成功することである。QuickJSのエラーや停止がUIを終了させず、停止後にエンジンとコールバックの資源が解放されることを確認する。

### 段階6：QuickJSから開発者のnativeコードを利用

1. muonの型情報とネイティブ呼び出しをQuickJSのモジュールへ公開するアダプターを作る。
2. サンプルのC/C++ライブラリーをSDKでビルドし、TSサービスから同期・非同期処理とコールバックを利用する。
3. 引数・戻り値、バイナリー、64bit整数、エラー、解放順序を両プラットフォームで検証する。

完了条件は同じTSサービスと共通C/C++ソースの組み合わせをAndroidとPCで動かせ、サービス停止後にコールバックやライブラリー参照が残らないことである。

### 段階7：PC用Node.jsアダプター

1. 既存サイドカーの所有者をホストへ変更する最小ドライバーを作り、UI終了後の実行と非同期停止を試験する。
2. 共通SDKと同じメソッド・購読を実装できるか検証し、Node.js固有部分と共通部分を明示する。
3. 実現可能な場合はビルド・配布をサービスの実装指定へ接続し、同じインターフェイスのNode.jsサンプルを公開する。共通部分に大きな追加制約を要する場合は、その根拠を記録して独立した拡張として扱う。

完了条件は対応する場合にLinux・Windowsで共通の寿命・通信テストが成功し、UI終了がNode.jsプロセスを終了させないことである。保留する場合は、最小ドライバーで判明した制約と必要な変更を記録し、未対応の設定をビルド時に明確に拒否する。

### 段階8：独立した利用側と全体検証

1. 公開NPMパッケージから独立した利用アプリを作り、native・QuickJSと、対応した場合のNode.jsサービスをビルドする。
2. Androidの署名済みAPK・AAB由来APK setと、PCの配布物で、UIの終了・再表示、設定の保存、複数サービス、双方向通信を確認する。
3. SDKと利用方法の日本語原本を更新し、他言語版へ反映する。動作条件、OS制限、UIの終了とアプリ全体の終了の違いを記載する。
4. 関連試験、以下のAndroid端末試験、PCの実行試験、最後に全体`npm test`を実行し、実行環境と未検証範囲を記録する。

完了条件は開発者が配布パッケージだけでサービスを実装・ビルド・実行でき、対象OSの寿命・設定・通信を実証し、全体テストが成功することである。

## Androidの検証計画

Androidの検証には既存のnativeテストホスト、QuickJSの試作、独立したobserverアプリを使う。各段階で実行できるドライバーを追加し、共通の寿命管理とAndroid固有の動作を分けて検証する。

### 現在利用できる基盤

- `core/common-test`は共通C/C++コードをホストで実行できる。参照管理と状態遷移の試験をここへ追加する。
- `core/android-test`はWebView、RPC、native plugin、Activity再生成、資源解放を検証する。
- `core/android-poc`は別プロセスのQuickJS Service、複数runtime、通信、Serviceプロセス終了後の再接続を検証する。
- `core/android-test/observer`は対象アプリとは別のAPKで動作し、独立してビルドした利用アプリを操作する。
- `ui/android-test/test-packaged-application.mjs`はnpm配布物を独立した利用アプリへ導入し、公開CLIによるビルドと端末での操作を検証する。

現在のQuickJS Service試験は、今回提案する自動起動や常駐参照の規約を検証したものではない。また、既存のrelease試験はAPKとAAB由来のAPK setについて、起動後のpage-readyを確認する。UI終了後の処理継続、常駐設定の変更、サービスへの再接続は新たに追加する。

### 共通の寿命管理を先に検証する

OSを起動しなくても実行できる試験で、次の振る舞いを確認する。

1. 同時に複数の`acquire()`を行っても、同じサービスの起動は1回になる。
2. `release()`の重複や、ページ破棄との競合で参照を二重に解放しない。
3. 自動起動を何度ONにしても、常駐参照は1つだけになる。
4. OFFは常駐参照だけを解放し、ページの参照と実行中の利用を保護する。
5. 最後の参照を解放すると停止し、停止中の再取得は古い世代の停止完了後に処理する。
6. ON→OFF→ONの途中で古い起動・停止が完了しても、最新の設定を上書きしない。
7. 起動失敗、設定保存失敗、取得元ページの消失で、未確定の参照が残らない。
8. サービスAの正常停止はサービスBの参照や実行状態へ影響しない。共有プロセスの異常終了は別に検証する。
9. 状態の監視だけではサービスの寿命を延ばさない。
10. 世代終了後の古いハンドルは呼び出しを拒否し、その解放が新しい世代の参照を減らさない。

競合はsleepや反復回数で発生を期待せず、テスト用サービスに起動・停止の待機点を設ける。試験側が待機点への到達を確認し、競合する操作を行ってから処理を再開する。待機のタイムアウトは試験が停止したことを検出するために使い、成功の判定には使わない。

この方法はAndroid側にも適用する。既存QuickJS並列試験の`CountDownLatch`と、native試験の実際のidle状態を待つ仕組みを参考にする。

### UIとサービスの寿命を端末で確認する

native版とQuickJS版で同じ操作を実行できるドライバーを用意する。ドライバーは自動起動スイッチ、サービスの取得・解放、要求の送信、受信結果、実際の動作状態を表示する。

| 操作 | 期待する結果 |
| --- | --- |
| ページAとBが同じサービスを取得する | 同じ世代を操作でき、起動が重複しない |
| Aを破棄してBから要求を送る | Bの要求とコールバックが成功する |
| 自動起動ONで全Activityを終了する | UIがなくてもサービスが仕事を完了する |
| UIを再表示してサービスを取得する | 継続していたサービスへ接続し、結果を取得できる |
| ページ参照を残して自動起動をOFFにする | 設定はOFFになり、既存利用者の処理は継続する |
| 自動起動OFFの状態で最後のページ参照を解放する | サービスが停止し、所有する資源が解放される |
| 自動起動設定を変更してアプリを再起動する | 保存した設定を復元する |
| サービスAを正常停止してBへ要求を送る | Bの処理が成功する |

PIDの存在や参照数だけで継続動作を判定しない。例えば、独立した試験側サーバーが応答を保留し、UIの終了を確認してから応答を返す。サービスからの完了通知を受け取り、再表示したUIでも結果を確認する。これにより、UI終了後に実際の処理が進んだことを検証する。

UIプロセスの終了を伴う試験は、対象アプリ内のinstrumentationから実行せず、独立observerから操作する。observerが対象サービスへbindしたり参照を取得したりすると、その接続が寿命を延ばす可能性があるため、継続検証ではそのような接続を持たせない。試験用の強制終了操作や内部状態の取得機能はdebug試験へ限定する。

### 終了の種類を分けて扱う

| 終了操作 | 確認する動作 |
| --- | --- |
| ページ破棄・Activity終了 | UI所有参照を解放し、常駐参照があればサービスを継続する |
| タスク一覧からの除去 | Activity終了とは別に検証し、サービス構成で定めた挙動に従う |
| UIプロセスだけの異常終了 | UI所有参照を回収し、常駐参照のあるサービスの継続を確認する |
| Serviceプロセスだけの異常終了 | 未完了要求を失敗させ、古い通知を破棄し、次の取得で再接続できる |
| `am force-stop` | アプリ全体の強制停止として扱い、通常のUI終了の代用にしない |
| AndroidのActive appsからの停止 | アプリ全体の停止を受け入れ、終了コールバックに依存しない |

AndroidのActive appsからの停止は、`adb shell cmd activity stop-app PACKAGE_NAME`で再現できる。OSはアプリ全体を停止し、終了コールバックを通知しない。設定は各更新時に保存し、明示的にアプリを再起動した後にも保存済みのOFFが維持されることを確認する。[Androidのユーザー操作による停止](https://developer.android.com/develop/background-work/services/fgs/handle-user-stopping)

### Android固有の制約を確認する

- UIからのforeground service起動成功と、許可されないバックグラウンド起動の失敗を確認する。
- 用途に対応したservice type、権限、通知が生成され、必要な権限がない場合に失敗理由を返すことを確認する。
- 通知権限の許可・拒否をそれぞれ試し、設定上の自動起動状態と実際の実行状態を混同しない。
- native初期化を保留しても、foreground化と通知の準備を遅らせないことを確認する。
- OSによる実行時間制限を受けたときに停止し、自動起動ONを理由とした再起動ループを起こさないことを確認する。
- OS起動イベントへの対応を実装する段階では、対象の用途と権限で許可される条件だけを検証し、PCのログイン起動と同じ保証を与えない。

バックグラウンド起動の試験では、対象アプリの可視Activityやinstrumentation、試験側からの接続が起動条件を変えていないことを確認する。起動の例外条件と、カメラ・位置情報などの使用中権限の条件は[foreground serviceの起動制限](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start)に従う。用途と必要な宣言は[service typeの一覧](https://developer.android.com/develop/background-work/services/fgs/service-types)を参照する。

`dataSync`などの時間制限試験には使い捨てVMで公式の`device_config`による制限時間の短縮を利用する。変更前の設定を記録し、試験終了時に復元する。長時間のsleepで制限到達を待つ試験にはしない。[foreground serviceのタイムアウトと試験方法](https://developer.android.com/develop/background-work/services/fgs/timeout)

### 端末と配布物の検証範囲

現在のrelease試験には、次の2つの固定プロファイルがある。試験開始時にAPI、ABI、実際のページサイズを検査する。

| プロファイル | OS | ABI | ページサイズ |
| --- | --- | --- | --- |

Androidでも同じC99ライブラリーとTSサービスを公開SDKでビルドし、生成APKから実行できた。Pixel 6と16 KiBエミュレーターで、バイナリー、64bit整数、再入コールバック、関数プロキシ、イベント、複数サービス、世代の切り替えを確認した。UIプロセス終了後の実処理と同じ世代への再接続、最後の停止後のnativeランタイム再読み込みも成功した。既存のサービスobserverとソース読み込み・dispatcherの回帰試験も両環境で成功した。

段階7は実装可能性を調べるドライバーを作り、Node.jsサービスの製品への組込みを独立した拡張として保留する。共通SDKをNode.jsで動かせないことが理由ではない。既存のページ用サイドカーを再利用するには、サービス用の所有者管理と停止処理を追加する必要があり、そのまま組み込むと共通の寿命規約を満たさないためである。

[Node.jsの寿命検証ドライバー](../../../node/test/service-host-probe.test.ts)では、Linux上でドライバーが既存サイドカーの通信路を所有する。UIを模した別プロセスが終了するまでHTTP応答を保留し、終了後に応答を返した。共通SDKのサービスメソッドがその後に完了し、イベントも発生した。実CEFを組み込んだNode.jsサービスの試験ではない。

同じドライバーでサービスの終了処理をHTTP応答待ちにした。サービスの終了完了を待ってからサイドカーを閉じる場合は、終了処理がファイルへ完了を記録した。一方、既存の `shutdown` を先に送る場合は、未完了の終了処理があっても子プロセスが終了し、完了記録が残らなかった。この差は、要求到着と応答解放の順序を固定して確認した。このドライバーの2シナリオを含む、Node.js側の全42件の試験が成功した。

[既存nativeプラグインの接続ドライバー](../../../core/cef-test/service-node-probe.test.ts)では、実際の独立サービスホストから既存のNode.jsプラグインを読み込んだ。`createNode` はページ所有者のトークンを必要として開始に失敗した。全操作を許可しても、関数を個別に公開するサービス用モジュールと、単一のNode facadeを公開するページ用プラグインでは公開方法が異なり、接続できなかった。2シナリオとも失敗理由を観測した後にホストが正常終了することを確認した。

さらに、[既存Node.jsプラグイン](../../../node/native/node_plugin.cpp)はWindowsでDLLをプロセス終了まで保持する。ページ用の終了処理はこの前提を持つため、サービス用のnativeプールへ移すだけでは最後の所有者の解放でライブラリーを解放する規約と合わない。今回、Windows上のNode.jsサービスとしての動作は検証していない。

次の拡張では、既存の子プロセス起動・認証・通信処理を利用しながら、ページ用プラグインから独立したサービス用アダプターを設ける。サービスのIDと世代に所有者を結び付け、開始・呼び出し・キャンセル・非同期停止の完了をホストへ接続する。呼び出しに付随するコールバックと長期のイベント通知を分け、子プロセスの異常終了、停止期限、Windowsの後片付けと再起動を検証する。Node.jsプロジェクトと実行環境の配布も、このアダプターへ接続する。

公開ビルダーは引き続き `runtime: "node"` を、未対応のサービス方式としてビルド時に拒否する。ページ側の既存Node.js機能は維持する。段階7の保留判断は完了したが、計画全体の配布物検証と最終の全体テストは継続中である。
