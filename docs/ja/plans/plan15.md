# Linux Waylandでの起動失敗とViteの終了通知の修正計画

## 目的と対象

LinuxのWaylandセッションで、環境変数によるX11への切替をせずにmuonアプリのウインドウを開けるようにする。また、muonの子プロセスが異常終了した場合に、Viteの利用者が原因と失敗を確認できるようにする。

muonのエンドユーザーが、デスクトップ環境やホストのGTKの版に合わせて起動方法を調整せずに使えることを重視する。今回再現したUbuntuだけで修正を判断せず、既存の対応範囲で複数の環境を検証する。GTKの版によるX11への自動切替は追加せず、WaylandとX11の両方を維持する。

調査の起点は、Chronical Decadeで`npm run dev`を実行すると、ウインドウが表示されずにViteが終了する問題である。修正対象はmuon-uiのLinux配布ランタイムとViteプラグインとする。ランタイムとは、アプリの実行に必要なmuon-core、CEF、共有ライブラリーなどをまとめた配布物を指す。GTKはLinuxのウインドウやダイアログに使うライブラリーで、GDKはその画面システムとの接続を担う部分である。

作成日は2026年10月22日。muon-uiの調査基準は`develop`の`0b4e8c27d9fd58ba7b6a2ada73d4bd8c93ce9966`、問題を再現した利用側の依存は`muon-ui@0.32.0`である。以下は作成時の計画を保持し、実装と検証の結果を末尾に追記する。

## 確認した原因

Ubuntu 24.04.5のWaylandセッションでViteの起動までは成功したが、muon-coreが次のエラーを出して`SIGTRAP`で終了した。調査では一時的な起動スクリプトから子プロセスの標準エラーを取得し、利用側のソースやインストール済みパッケージは変更していない。

```text
GLib-GIO-ERROR: Settings schema 'org.gnome.settings-daemon.plugins.xsettings'
does not contain a key named 'antialiasing'
```

GSettingsはGNOME系の設定を読む仕組みで、スキーマは設定キーの名前と型を定義する。今回のランタイムにはUbuntu 20.04由来のGTK `3.24.20-0ubuntu1.2`と、muonが別途ビルドしたGLib 2.74.7が含まれていた。GTK 3.24.20のWayland実装は旧スキーマの`antialiasing`などを参照するが、実行ホストの旧スキーマにはそのキーがなかった。[GTK 3.24.20の該当処理](https://github.com/GNOME/gtk/blob/3.24.20/gdk/wayland/gdkscreen-wayland.c#L347)

さらに、[Viteの起動処理](../../../ui/cef/vite-internals.ts)が子プロセスを`stdio: "ignore"`で起動し、終了シグナルを保存していなかった。終了コードが88の場合はmuonを再起動するが、それ以外は正常終了と異常終了を区別せず、既定の設定でViteを閉じる。このため、GTKのエラーが見えず、Vite自身は終了コード0で終了していた。

次の環境変数を組み合わせると、同じ配布物でChronical Decadeのウインドウと地球の描画を確認できた。`GDK_BACKEND=x11`だけでは再現を回避できなかったため、GTKだけのバックエンド指定を恒久修正にはしない。

```sh
XDG_SESSION_TYPE=x11 WAYLAND_DISPLAY= GDK_BACKEND=x11 npm run dev
```

## 修正方針と比較した案

GTK 3.24.52を、現在と同じUbuntu 20.04のビルド環境でソースからビルドし、GDKとともに配布ランタイムへ組み込む。配布先のOSに必要なシステムライブラリーの最低条件を不用意に引き上げず、Waylandでの設定参照を修正した上流実装を使う。

GTK 3.24.52の公式ソースには、`org.gnome.desktop.interface`の`font-antialiasing`、`font-hinting`、`font-rgba-order`を使い、旧環境では従来の設定へ戻る処理がある。今回のホストで欠けていた旧キーを無条件に読む問題に対応できると判断した。ただし、まだmuonの配布物としてビルド・実行していないため、段階2で実証する。任意の壊れたスキーマまで扱えるとはみなさない。[GTK 3.24.52の設定参照](https://github.com/GNOME/gtk/blob/3.24.52/gdk/wayland/gdkscreen-wayland.c)

| 案 | 判断と理由 |
| --- | --- |
| 同梱GTK/GDKを3.24.52へ更新 | 採用する。上流の設定参照を利用でき、Waylandとユーザーの現在のフォント設定を維持できる見込みがある。モジュールと依存ライブラリーを含めて検証する。 |
| 旧GSettingsスキーマを同梱し、`GSETTINGS_SCHEMA_DIR`で優先 | 採用しない。新しいデスクトップの設定との対応をmuon側で維持する必要があり、ユーザーが現在使う設定を反映できない可能性がある。 |
| X11を強制 | 一時的な回避策とする。Waylandでの起動という完了条件を満たさない。 |
| `GSETTINGS_BACKEND=memory`を既定値にする | 採用しない。保存先の切替であり、欠けているスキーマキーを補う処置にはならない。設定値の永続化も変わる。[GSettingsの説明](https://docs.gtk.org/gio/class.Settings.html) |
| ホストのGTKを直接使う、またはビルド基準を新しいUbuntuへ変更 | 今回は採用しない。配布物の依存解決や対応OSの条件まで変更する必要がある。 |

GLibは現在の2.74.7を維持する。GTK 3.24.52が要求するGLibとMesonの最低版は現在の構成で満たせるが、その他の開発パッケージと3アーキテクチャでの成立は実ビルドで確認する。新たな依存関係の問題が出た場合は、場当たり的に多数のライブラリーを更新せず、必要条件と本計画を見直す。[GTKのビルド条件](https://github.com/GNOME/gtk/blob/3.24.52/meson.build)

上流GTKやCEFのソースにはパッチを加えない。ホストのスキーマやユーザーのデスクトップ設定も変更しない。NPMへの公開、mainへのマージ、Chronical Decadeの製品コード変更は本計画の対象外とする。

## エンドユーザー環境を基準にした検証

環境の違いを次の軸に分けて検証する。ネイティブの小さな動作テストで設定や依存関係の違いを広く調べ、代表的な実デスクトップでは配布アプリ全体の操作を確認する。

| 環境の違い | 必須の確認内容 |
| --- | --- |
| 古いシステムと新しいシステム | Ubuntu 20.04を基準にした従来環境とUbuntu 24.04で実行する。新GTKをビルドできただけで判断せず、配布物が要求するシステムライブラリーとシンボルの最低条件を確認する。 |
| WaylandとX11 | 両方で起動、描画、入力、ファイルダイアログを確認する。Wayland試験は使用バックエンドを記録し、XWayland経由の成功と区別する。 |
| GNOMEとGNOME以外 | GNOMEに加え、KDE Plasmaを代表例として実デスクトップで確認する。Westonの隔離試験も併用し、GNOME固有の常駐サービスを起動の前提にしない。使用したディストリビューションと版を実施記録に残す。 |
| GNOMEの設定スキーマ | 旧キーがある環境、新キーへ移行した環境、GNOME向けの設定スキーマがない環境を試す。存在する設定は反映し、GNOMEのフォント設定がない場合は既定値で起動できることを確認する。 |
| 設定を提供するデスクトップサービス | GSettingsによる参照と、デスクトップの設定を提供するSettings portalがある場合を試す。任意のサービスがない条件も隔離環境で確認する。 |
| ホストにあるGTK関連ファイル | ホストの開発パッケージや偶然存在するモジュールに頼らず、配布物と既存の実行要件だけで動作することを確認する。GTK自身に必須のデータと、GNOMEから提供される任意設定を区別する。 |
| 入力とファイル選択 | 単純な英数字入力だけでなく、日本語入力、IBus/Fcitx系のモジュール読み込み、ファイルダイアログ、画像表示を確認する。 |

ここでいう「スキーマがない環境」は、ホストのファイルを削除して作らず、コンテナーなどで設定の探索先を隔離する。`GSETTINGS_SCHEMA_DIR`へ空ディレクトリーを指定しただけでは、既定の探索先が残る可能性があるため、実際に見えているスキーマを確認する。

GTK自身が必要とする設定スキーマなどのデータに配布漏れが見つかった場合は、そのGTK版に対応するデータを配布し、出自と探索先も管理する。旧GNOMEスキーマを優先して今回の問題を回避する案とは分けて扱う。Settings portalや設定スキーマの有無による挙動は、上流の[Wayland設定初期化](https://github.com/GNOME/gtk/blob/3.24.52/gdk/wayland/gdkscreen-wayland.c)と実行結果を照合する。

## 追加のユーザー意向

計画作成中に「エンドユーザーを考慮して、様々な環境で問題なく動作するようにしたい」「GTKのバージョン制約でX11へフォールバックするのか」という意向と質問を受けた。X11への切替は調査時の一時的な回避策であり、恒久修正として強制しないことを確認した。検証範囲をGNOME以外や任意の設定がない環境まで明示し、配布物自身が持つべき依存関係とホストから受け取るデスクトップ設定を分けて確認する方針にした。

## 段階1：Viteで異常終了を確認できるようにする

最初に診断を修正し、その後のGTK検証でも失敗理由を取得できる状態を作る。この段階だけでテストを実行し、独立した修正としてコミットする。

1. 偽のmuon実行ファイルを実際に起動するテストを追加する。既知のメッセージを標準エラーへ書いて非ゼロ終了する場合と、POSIXで`SIGTRAP`終了する場合に、診断表示とVite CLIの終了コードが期待どおりにならないことを確認する。CLIは別のNode.jsプロセスで起動し、テストランナーの終了コードを汚さない。
2. 子プロセスの終了を終了コードとシグナルの組として扱い、標準出力・標準エラーを継続して読み取る。診断用に保持する量は合計64 KiBを上限とし、末尾の出力を保存する。上限到達後も読み取りを止めず、UTF-8の分割と大量出力による停止を避ける。
3. 予期しない終了では実行ファイル、終了コードまたはシグナル、取得した診断をViteのloggerへ出力する。出力がない場合でも終了理由は表示する。通常の終了と終了コード88による再起動では異常として表示しない。
4. 既定の`exitWithServer`では、異常終了の診断後にViteを閉じ、CLIが非ゼロで終了するようにする。`process.exit()`で強制終了せず、未設定または0の`process.exitCode`を1にする。既存の非ゼロ値は保持する。`exitWithServer: false`では診断を表示してViteを維持し、プロセス全体の終了コードは変更しない。実行ファイルの起動自体に失敗した場合も同じ方針で扱う。
5. Vite側からの通常停止による子プロセスの終了は異常扱いしない。supervisorの完了後にサーバーを閉じる構造とし、`server.close()`からcleanupを経由して自分自身の完了を待つ循環を作らない。後処理を含むPromiseは`await`で回収する。
6. 追加テストを成功させ、既存の正常終了、再起動、サーバーの継続、終了処理のテストも確認する。64 KiBを超える出力と、終了直前のエラーメッセージを含むケースで、停止や診断の欠落がないことを検証する。親からの停止と子の終了が競合するケースも加え、プロセスの終了を待って判定する。待機の上限は循環待ちを検出するために設ける。

完了条件は、数値による失敗とシグナルによる失敗の両方をCLIから判別でき、`exitWithServer: false`、終了コード88、親からの正常停止が従来の用途を満たすことである。コミット例は`fix: report muon runtime failures from Vite`とする。

## 段階2：配布GTKを更新し、Waylandの設定参照を直す

最初に現在の配布ランタイムで失敗するネイティブの小さなテストを作る。GTKを初期化し、Wayland接続とフォント設定の取得まで実行する。Ubuntu 24.04の実スキーマを使い、新しいフォントキーが存在し、旧キーが存在しない条件で失敗を確認する。ソース中の文字列やバージョンの一致だけを検証するテストにはしない。

同時に、同じ環境で現在の配布muon-coreがウインドウを開けないことを記録する。段階3の公開起動経路のテストでも、この未修正版を比較対象に使えるよう保存する。

GTKの追加ビルドには次を固定する。

| 項目 | 値 |
| --- | --- |
| バージョン | GTK 3.24.52 |
| ソース | `https://download.gnome.org/sources/gtk/3.24/gtk-3.24.52.tar.xz` |
| SHA-256 | `80931fa472a77b9a164f6740e3c0b444fac6770054632d35a7ff9d679e5e7b9f` |
| インストール先 | `/opt/muon-gtk` |
| バックエンド | X11とWaylandの両方 |

ソースとチェックサムは[GNOMEの公式配布](https://download.gnome.org/sources/gtk/3.24/)と[公式チェックサム](https://download.gnome.org/sources/gtk/3.24/gtk-3.24.52.sha256sum)を使う。追加する外部APIやビルドオプションは、実装時に公式文書と対象バージョンの宣言・コメントを照合する。

1. `linux-baseline.Containerfile`にGTKのビルドと出自情報を追加する。ビルド時の`PKG_CONFIG_PATH`とライブラリー検索順序を明示し、GLibは既存の私有版、GTK/GDKは新しい私有版へ解決させる。ホストの`/usr`へ上書きしない。
2. 依存収集処理で新GTK/GDKとその付属モジュールを選択する。新しいGTK用の検索ツールで入力メソッドのキャッシュを生成し、IBus、Fcitx、Fcitx5の既存モジュールも保持して動作を確認する。旧GTK付属モジュールの再混入や、同名モジュールの二重登録を避ける。
3. 画像読み込み用のgdk-pixbufとGIOは、現在の依存構成を基に互換性を検証する。これらを一律にGTKと同じprefix由来とみなさず、各モジュールとキャッシュの生成元を区別する。配置先の`linux/lib`形式と既存のキャッシュ再配置を維持する。各キャッシュが指すモジュールの実体を確認し、ビルド時の絶対パスが配布物に残らないことを検証する。
4. ELFの依存検査で、GTK/GDK、GLib、Pango、Cairo、ATKなどの実際の解決先と必要なシンボルを確認する。各モジュールが`DT_NEEDED`に記録する依存ライブラリーも検査に含める。意図した依存構成を検証し、ホストにある偶然のライブラリーで不足を補っていないことを確かめる。
5. `source.json`と`linux-bundle.json`にGTKの出自、ハッシュ、ライセンスを記録し、各共有ライブラリーとモジュール・キャッシュの帰属を検証する。現在のGLib専用の型・読み込み処理と出自記録への引数をGTKにも対応させ、GTKのライセンスファイルを専用prefixへ配置する。GTKとGLibのprefixを分けることで、現在のprefixによる帰属判定でも区別できるようにする。
6. 旧版で失敗したテストを更新した配布ランタイムで成功させる。新しいGNOMEの設定値がGTKへ反映されることと、従来の設定環境やGNOME向けのスキーマがない環境でも起動することを確認する。設定値の試験には隔離した保存先を使い、デスクトップ設定の保存先であるユーザーのdconfを変更しない。GTK自身の必須データに不足があれば、その不足による失敗を先に確認してから配布処理を修正する。

ビルドイメージは存在確認だけでは更新されないため、`prereq.sh --force`で再作成してから配布物をビルドする。最初はamd64で再現と修正を確認し、段階4で全アーキテクチャへ広げる。ビルド警告は内容と出所を確認し、未解決のまま成功としない。

完了条件は、Ubuntu 24.04のスキーマを使うWaylandでネイティブテストと配布muon-coreが起動し、GNOME向けの設定がない場合、X11の既存動作、入力メソッド、画像読み込み、出自記録も成立することである。コミット例は`fix: bundle GTK with current GNOME Wayland settings support`とする。

## 段階3：利用者と同じ起動経路を回帰テストにする

段階2の配布物をNPMパッケージにまとめ、独立した最小アプリへインストールする。リポジトリーの開発ビルドやホストGTKだけで通るテストを避け、実際に利用者へ渡すランタイムの動作を検証する。

1. Westonで隔離したWaylandセッションを用意する。Ubuntu 24.04のスキーマを利用し、段階2で保存した未修正版が失敗することを同じテストで確認する。待機はプロセス、通信、ページの準備完了を条件にし、一定時間生存しただけでは成功としない。
2. Viteからの起動、`muon run`、ビルド済み配布物のランチャーを順に確認する。Playwright MCPでアプリのページへ接続し、DOMの準備完了と簡単な描画を検証する。Wayland専用の試験では、テスト対象の`DISPLAY`を空にしてWestonのソケットを渡す。GDKとCEFが実際に利用したバックエンドを確認し、X11への切替で通ったケースをWaylandの成功として数えない。通常のデスクトップ環境を引き継ぐ試験も別に行う。
3. 正常終了、Vite停止、再起動要求を実行し、子プロセスや一時プロファイルが残らないことを確認する。X11でも同じ起動経路のスモークテストを行う。
4. 空の`.muon`からの起動に加え、旧版を準備済みの状態でパッケージを更新して起動する。新しい配布ファイルが再配置され、手作業でのキャッシュ削除を要しないことを確認する。ここで再配置の不具合を実証した場合に限り、準備処理の該当部分へ再現テストと修正を追加する。
5. CIにUbuntu 24.04を明示したWayland起動テストを追加する。Westonと必要なGNOMEスキーマを導入し、必須ジョブでは前提が欠けた場合にスキップせず失敗させる。CIのログには子プロセスの診断、使用バックエンド、読み込んだライブラリーの確認結果を残す。

既存の`core/cef-test`、Wayland補助スクリプト、パッケージ検証処理を利用し、専用の大きなテスト基盤は増やさない。`verify-package-runtime`によるファイルとライセンスの検証も続けるが、ウインドウ起動の代替にはしない。

完了条件は、公開する3種類の起動経路で未修正版の失敗と修正版の成功を確認し、Waylandの回帰テストをCIで必ず実行できることである。コミット例は`fix: cover packaged runtime startup on Wayland`とする。

## 段階4：配布対象全体とChronical Decadeで確認する

Linuxの配布対象であるamd64、armhf、arm64を既存のビルド手順で作成し、依存関係、シンボル、モジュール、キャッシュ、ライセンスを検査する。スクリプトへ渡すアーキテクチャ名は`amd64,armv7l,arm64`であり、`armv7l`が配布名のarmhfに対応する。

```sh
bash prereq.sh --arch amd64,armv7l,arm64 --force
bash build_package.sh --target dist --arch amd64,armv7l,arm64
npm run verify:package-runtime --workspace muon-ui
npm test
```

WaylandとX11の実起動はamd64で必須とし、ARMは既存の実行環境・エミュレーションで起動とモジュール読み込みを確認する。ARMの実Wayland環境で確認できない項目は未実施として記録し、依存検査だけで実機確認済みとはしない。新GTKに必要な命令セットやシステムライブラリーの条件が対象ごとに変わっていないことも確認する。

前述の環境ごとの検証表に結果を対応付け、GNOMEとKDE Plasmaの実セッションで配布アプリを確認する。起動だけでなく、文字入力、日本語入力、ファイル選択、描画、終了を実行する。利用できるテスト環境がない項目は未確認として残し、すべての環境で検証済みと報告しない。

Viteの変更は共通のJavaScript処理へ影響するため、Linuxだけの個別テストで完了にせず、リポジトリー全体の`npm test`を実行する。Windowsを含む既存の実行先が必要なテストも現在の手順に従う。環境上の実行不能は成功扱いせず、理由と未確認項目を記録する。時間がかかるテストには妥当な上限を設定し、タイムアウトを避けるためだけに検証を削らない。

最後にChronical Decadeの一時チェックアウトへ修正版のローカルNPMパッケージを導入する。元の作業ツリーと依存定義を変更せず、通常のWayland環境で、X11へ切り替える変数を付けない`npm run dev`を実行する。Playwright MCPでウインドウ、ページの準備完了、地球の描画を確認する。

利用文書にはViteの異常終了ログと終了コード、`exitWithServer: false`の動作を記載する。日本語のViteプラグイン説明を原本として英語版へ反映し、外部ライブラリーの制約を書く場合は公式情報へリンクする。内部のビルド手順を一般のREADMEへ追加せず、本計画書にも一般の利用文書からリンクしない。文書のコミット例は`doc: describe Vite runtime failure diagnostics`とする。

## 実装と検証の記録

2026年10月22日に`feature/plan15`で実装を開始した。ここからは計画作成後の記録であり、上記の「計画作成時の完了条件と記録」と区別する。検証環境はUbuntu 24.04.5、amd64、GNOME Waylandである。

### Viteの診断と終了処理

終了コード、シグナル、実行ファイルの起動失敗を診断し、標準出力と標準エラーの末尾を合計64 KiBまで保持するようにした。UTF-8の文字がチャンク境界で分割されても、途中のバイト列を置換文字として出力しない。既定ではViteも閉じて終了コードを1にし、すでに設定された非ゼロ値は保持する。`exitWithServer: false`では診断だけを表示する。

正常終了、終了コード88、親からの停止、長い出力、終了直前の出力、終了処理の競合を含む回帰テスト104件が成功した。supervisorの完了後にViteを閉じることで、サーバー終了時のcleanupが自身の完了を待つ循環を解消した。親からの停止後に、一時設定ディレクトリーが実際に削除されることも確認した。

### GTKと配布データ

GTK 3.24.52を専用prefixでビルドし、既存のGLib 2.74.7と組み合わせた。GTK本体、入力モジュール、印刷モジュール、キャッシュは新しいGTKから収集する。外部のibus、Fcitx4、Fcitx5は引き続き配布物へ含める。Fcitx5のキャッシュが持つ`fcitx`互換名はFcitx4と重複するため、Fcitx4の`fcitx`とFcitx5の`fcitx5`をそれぞれ選べるように整理した。

GNOME設定がない条件では、GTK自身のスキーマだけでなくMIMEデータとhicolorアイコンテーマの定義も必要だった。これらを除いたテストでファイル選択の失敗を確認した後、GTKの`gschemas.compiled`、`mime.cache`、`hicolor/index.theme`を配布物に追加した。起動時は配布物の`linux/share`を`XDG_DATA_DIRS`の先頭に置き、既存の検索先も保持する。古いGNOME設定スキーマは配布物へ追加していない。

amd64・ARMhf・ARM64のELF依存監査では、依存先やシンボルの問題を記録する`issues`は0件だった。GTKの版、外部モジュールの依存先、再配置用キャッシュ、各ファイルの出自とライセンスを確認した。各配布物の69項目について、内容のハッシュ、25件のライセンス本文、63個のELFのアーキテクチャも一致した。ARMhfのDebianパッケージ情報から出た警告5件は、後述のとおり実ライブラリーのシンボル解決と分けて確認した。GTKとGLib以外の主要な版は従来どおりで、Pango 1.44.7、Cairo 1.16.0、ATK 2.35.1、GdkPixbuf 2.40.0を維持している。amd64の旧配布物との依存一覧の比較でも、システムライブラリーに要求する最低版は上がっていない。

追加依頼に従い、ビルド後のGTK参照先も確認した。amd64の開発・テスト用バイナリは、ReleaseとDebugの両方でシステムの`/lib/x86_64-linux-gnu/libgtk-3.so.0`を使用する。一方、amd64・ARMhf・ARM64の配布用バイナリは、`muon-core`から`libmuon-ui.so`を経由し、同じ配布ディレクトリーの`libgtk-3.so.0`を参照する。ELFのライブラリー検索先は実行ファイルの配置先を表す`$ORIGIN`であり、ビルド環境の絶対パスは埋め込まれていない。3配布対象の`ldd`検査では`LD_LIBRARY_PATH`と`LD_PRELOAD`を外し、配布物内のGTK/GDKへ解決され、未解決の共有ライブラリーがないことを確認した。開発・テスト用にも未解決の共有ライブラリーはなかった。

ARM64ではCEFのCDP接続先も開いたが、MCPによる画面検証の前にGPUプロセスが`error_code=1002`で繰り返し失敗し、終了した。同じUbuntu 20.04コンテナー、QEMU、Xvfbの条件でGTKとGDKだけを元の3.24.20に戻しても再現した。この比較では原因をQEMUと断定できず、ARM64のCEF画面検証は未完了とする。新旧GTK/GDKのELFヘッダーと属性には、追加の命令セット要件を示す差分はなかった。

ARMhfもCDPへの接続後、MCPでDOMや画面を確認する前にGPUプロセスの起動失敗で終了した。ログには`error_code=1002`、再試行後の`GPU process isn't usable`、シグナル5による終了が記録されている。ARMhfのCEF画面検証も未完了であり、ARM64と同じ原因とは断定していない。

GTKのファイル選択テストでは特定の入力デーモンへ依存しない入力コンテキストを使い、各外部モジュールのロードを別に検証する。GNOMEのibusセッションでFcitx4をファイル選択にも使用した試行では、[FcitxのD-Bus接続処理](https://github.com/fcitx/fcitx/blob/4.2.9.7/src/lib/fcitx-gclient/fcitxconnection.c)から警告が出た。デーモンを含むFcitx実環境での操作確認は未実施である。

### 公開起動経路と更新

旧GTKを残した独立NPM利用側で、Vite、`muon run`、ビルド済みランチャーの3経路が、新しいGNOME設定の`antialiasing`キー参照で失敗することを確認した。終了コードはViteと`muon run`が1、配布ランチャーが133だった。修正版ではWaylandとX11の3経路で、Playwright MCPによるページ表示と描画の検証が成功した。

終了処理は、Vite親プロセスの停止、`muon run`からの再起動要求、配布ランチャーからの通常終了を検証した。再起動前のmuonとCEF子プロセスが消滅し、別のPIDでページへ再接続できることを確認した。通常終了ではランチャーが終了コード0となり、終了後に関連プロセスは残らなかった。Wayland試験では`DISPLAY`を空にし、CEFの実行引数と同梱GTKのメモリーマップを確認した。GDKの型は、同じ配布物と環境を使うネイティブプローブでも検証した。

CIの実行環境をUbuntu 24.04に固定し、Weston、`gsettings-desktop-schemas`、`gnome-settings-daemon-common`を明示して導入する。新しい設定キーだけでなく、今回の問題に必要な旧スキーマも揃えた上で、ネイティブプローブと独立NPM利用側のWayland起動を必須の試験として実行する。

旧版の`.muon`を残してNPMパッケージを更新する試験では、GTKのハッシュが新しい配布物と一致するように変わり、更新後のライブラリーを実際にロードした。Playwright MCPでページを確認し、タイトルバーから閉じると終了コード0になった。手作業での`.muon`削除や準備処理の追加修正は不要だった。

描画の比較では、同じ`asset://`のCanvasがX11では旧GTK・新GTKともに正常で、Westonの隔離環境では両方とも透明な画素を返した。一方、通常のGNOME Waylandでは新GTKでも正常に描画できた。今回のGTK更新で生じた差ではないため、Westonの公開経路テストはCSSで描く矩形の実スクリーンショットを検証する。Canvasの結果はこの比較条件での観測に限る。

### ビルド警告の確認

GTKのビルドでは、Ubuntu 20.04のWaylandヘッダーに存在しない新しいコールバックの初期化子に警告が出た。GTKの[Waylandバックエンド](https://gitlab.gnome.org/GNOME/gtk/-/blob/3.24.52/gdk/wayland/gdkdisplay-wayland.c)は、この構成では`wl_output`と`xdg_wm_base`を対応する古いプロトコル版で使用する。警告対象の新しいイベントを要求しないことをソースで確認し、配布物のWayland起動でも確認した。

GTK内の未初期化変数に関する警告は、ポインターのNULL判定、項目が存在する条件、ジェスチャーが動作中である条件など、呼び出し側の前提をたどって確認した。カレンダーの書式文字列は上流で定義した固定の書式であり、利用者が与える文字列ではない。上流内の非推奨API、未使用変数、関数宣言に関する警告も確認した。これらの調査対象は[検証済みのGTK 3.24.52ソース](https://download.gnome.org/sources/gtk/3.24/gtk-3.24.52.tar.xz)であり、ベンダーコードへの変更や警告の一括抑制は行っていない。

ARMhfでは、ポインターの型変換先が要求するメモリー配置境界をコンパイラーが確認できない`-Wcast-align`警告も出た。[GObjectの型と確保方法](https://docs.gtk.org/gobject/concepts.html)、[Xlibのプロパティー取得仕様](https://x.org/releases/X11R7.7/doc/libX11/libX11/libX11.pdf)、各呼び出しの型タグや確保元を確認した。CSSの内部バッファーは構造体とポインター配列を交互に追加するが、ARMhfで必要な4バイト境界をどちらも保っていた。アイコンキャッシュも通常の生成処理が境界を揃えることを確認した。確認範囲はソース上の確保・配置条件と通常の実行経路に限られ、破損した外部キャッシュや任意のドラッグデータの扱いは未検証である。新旧GTK/GDKのELF属性では、ARMv7-A、VFPv3-D16、hard-float ABIなどが一致し、追加要件は観測されなかった。

ARMhfのC++ビルドには、引数の渡し方がGCC 7.1で変わったという通知も出た。これは[GCC 7のARM呼び出し規約の修正](https://gcc.gnu.org/gcc-7/changes.html)に対応する診断である。該当するSTLの処理は、現在のビルドで使用するGCC 10により再コンパイルされている。

ARMhfの依存情報を生成すると、5ファイルについて`__aeabi_atexit@CXXABI_ARM_1.3.3`が見つからないという警告が出た。[dpkg-shlibdeps](https://manpages.debian.org/bullseye/dpkg-dev/dpkg-shlibdeps.1.en.html)は、パッケージの`.symbols`から最低依存版を求める。今回のイメージにある[Ubuntuのlibstdc++6 10.5.0-1ubuntu1~20.04](https://launchpad.net/ubuntu/+archive/primary/+files/libstdc%2B%2B6_10.5.0-1ubuntu1~20.04_armhf.deb)を調べると、実ライブラリーはこの版付きシンボルを公開していたが、`.symbols`には記載がなかった。対象5ファイルをARMhf環境の`ldd -r`で検査し、未解決シンボルがないことを確認した。この記載の欠落は今回の環境での観測であり、実行時のリンク失敗やGCC 9との不一致ではない。依存情報に残る警告は隠していない。

Androidのlibffi構成時に表示されたClangの`-print-multi-os-directory`エラーは、configureによる機能検出の結果だった。構成処理は代替の判定で続き、ビルドは成功した。今回の変更で追加したCプローブは`-Wall -Wextra -Werror`でビルドし、警告がないことを確認した。

### Chronical Decade

元の作業ツリーを変更せず、`2936fa6`の一時チェックアウトへ修正版のローカルNPMパッケージを導入した。通常のGNOME Wayland環境を引き継いで`npm run dev`を実行し、X11へ切り替える環境変数は指定していない。並行するテストとブラウザープロファイルが衝突しないよう、保存先だけを一時領域へ分離した。

Playwright MCPでページの準備完了、muon APIの存在、WebGL2コンテキスト、地球の描画を確認した。スクリーンショットを目視し、地球の領域に複数の画素値が存在することも検証した。CEF子プロセスは`--ozone-platform=wayland`で動作した。最後にタイトルバーの閉じるボタンを操作すると、アプリとViteが終了コード0で終了した。

### 検証環境の補足と継続項目

Android StudioのSDKは`/home/kouji/Android/Sdk`に導入された。検証開始時点ではSDKがなかったため、指定のAndroid API 37、NDK 29、CMake 4.1.2とJDK 25を一時領域にも用意し、Androidビルドの成功を確認した。全体テストではその一時環境を使用した。

最初の全体テストではnpm 12の`npm pack --json`の出力変更により、既存テストの配列参照が失敗した。この変更は[npm 12.0.0のリリース情報](https://github.com/npm/cli/releases/tag/v12.0.0)に記載されている。npm 11.21.1を一時領域に導入すると、失敗していたSDKの独立パッケージテストは成功した。npm全体への対応変更は今回のGTK修正へ混在させず、最終的な全体テストはnpm 11で行った。

Linuxの既存CEFファイル選択テストでは、入力する英字パスがホストの日本語入力メソッドで変換され、選択に失敗した。画面で変換されたパスを確認し、テスト実行時だけ`GTK_IM_MODULE=gtk-im-context-simple`を指定すると、同じ検証が成功した。製品コードやユーザーの入力設定を変更する必要はなかった。

Windowsの実機テストでは、パス処理62件とbuilderのパス処理122件が成功した。先行したアプリ結合テストは、実行前のネットワーク疎通確認で失敗した。実機にある対象Node.js実行ファイルの受信拒否ルールを読み取りで確認しており、ファイアウォール設定は変更していない。

最終の全体テストでは、UIの509件が成功し、4件がスキップ、WindowsのNSISテスト3件が失敗した。2件はCDPのページ取得待ちでタイムアウトし、1件はWindows設定のアンインストール項目を操作できなかった。保存された画面では、対象アプリが設定画面に表示され、その前面にテスト用`relay.exe`のファイアウォール確認ダイアログが出ていた。このダイアログが設定画面の操作を妨げた可能性はあるが、2件のCDP失敗については通信、relay、ページ起動のどこで止まったかを既存ログだけでは区別できない。これらを成功扱いにはしない。

実機検証のために一時配置した2つのNode.js実行ファイルは、配置時のSHA-256と一致することを確認して削除した。残ったWindows Securityの確認画面はUI Automationから操作対象を取得できず、自動操作では閉じられなかった。ネットワークの許可操作やファイアウォールのルール編集は行っていない。

同じ全体実行で、SDKは18件、Android関連は110件・3件・40件が成功した。LinuxのC++テストはReleaseで61件が成功し、続くCEF結合テスト用にReleaseとDebugのビルドも成功した。LinuxのCEF結合テストは240件が成功し、33件がスキップ、1件が失敗した。失敗したのは、既定のファイル選択ダイアログを閉じた後に元のブラウザーへフォーカスが戻ることを確認する既存テストである。同じ環境でこのケースだけを実行すると2回とも成功し、全体実行時の失敗は再現しなかった。原因は未確定であり、個別実行の成功で全体実行の失敗を置き換えない。`npm test`全体の終了コードは1だった。

この既存テストのバイナリはシステムGTKを使用している。失敗時もファイル選択結果の取得とダイアログの消滅は確認できていた。テストは複数ワーカーでXvfbを共有し、別ウインドウへフォーカスを移す操作も行うため、終了後のフォーカスの移動先を調べる必要がある。現行ログにはそのX11ウインドウIDの履歴がなく、他のテストとの競合か単独でも起きる挙動かは区別できない。

前提イメージは3対象とも`--force`で再構築した。配布ビルドは実行時間を分散するため、`--arch arm64`と`--arch amd64,armv7l`に分けて実行し、両方とも成功した。その後に全対象をステージングし、`build_package.sh --target npm`でUIランタイム、SDK、配布ファイル一覧の検査が成功した。ローカル成果物は`artifacts/muon-ui-0.33.10.tgz`と`artifacts/muon-plugin-sdk-0.33.10.tgz`であり、公開していない。
