# muonプラグインSDKと外部開発・NPM配布

## 目的と承認された方針

muon-uiのソースリポジトリを取得・再ビルドせず、開発者がネイティブプラグインを開発、検証、配布、利用できるようにする。plan8で分離した共通C ABIと、Android・CEFの既存ランタイムを使用する。公開NPMパッケージ`muon-plugin-sdk`のコードを`sdk/`へ集める。

標準ビルドはMakefileとpkg-configとする。検討中の「pkginit」はpkg-configを指すと確認済みである。開発者が用意するCMakeなどの独自ビルドも同等に扱い、特定のビルドシステムを使用しないとSDKを利用できない構造にしない。実装言語はC99とC++20から選択し、既定はC++20とcardioとする。C版は公開C ABIと完了コールバックを使い、cardioへのリンクを必須にしない。

以下の四つの適用方法を正式に扱う。

| 適用方法 | 開発・利用の流れ |
| --- | --- |
| プロジェクト内だけのカスタムプラグイン | 自分のソースを標準または独自ビルドで生成し、アプリへ組み込む。プラグインごとのNPMパッケージは不要。 |
| vendor・submoduleなどで外部ソースを取り込む開発 | 外部ライブラリのビルド方式を利用し、自分の管理領域にmuon向け接続コードと設定を置く。既にmuonプラグインの形式を持つ外部プロジェクトも直接参照できる。 |
| ビルド済みNPMプラグインの利用 | パッケージ名からバイナリ、ヘッダー、TypeScript型、メタデータと依存物を解決する。利用者にネイティブコンパイルを要求しない。 |
| NPMプラグインの開発 | ローカルプラグインと同じ方法で開発し、対象別成果物を検証してNPMパッケージへ収録する。 |

外部ソースとnode_modulesをビルド出力先に使わず、開発者が管理する出力ディレクトリを用いる。ローカル専用として始めたプラグインを、同じ公開APIと成果物形式のままNPM配布へ移行できるようにする。

## 比較した案と採用理由

muon-uiへSDKを内蔵する案、独立SDKとビルド済みNPM配布を組み合わせる案、ソースとビルド手順をNPM配布して利用時にコンパイルする案、AAR・MavenをNPMで包む案を比較した。独立SDKとビルド済みNPM配布を標準に採用する。ローカルソースのビルドは同じSDKで扱う。AAR・Java/Kotlin・Androidリソースを含む拡張は将来の対象とし、今回のC/C++プラグインに必須としない。

参考としたemsdk-envは、外部パッケージのinclude・libをimportsから解決する。muonでは、作者が使用するネイティブライブラリというビルド依存と、アプリがロードする完成したプラグインという実行時依存を区別する。NPMの依存関係、ネイティブリンク依存、JavaScriptへの公開権限も別々に扱う。

- [emsdk-envの配布・参照仕様](https://github.com/kekyo/emsdk-env/blob/main/README_ja.md#npmパッケージにしてライブラリを配布)
- [pkg-config](https://wiki.freedesktop.org/www/Software/pkg-config/)
- [CMake Config package](https://cmake.org/cmake/help/latest/manual/cmake-packages.7.html)
- [Androidライブラリの配布](https://developer.android.com/studio/projects/android-library)
- [Androidネイティブ依存とPrefab](https://developer.android.com/build/native-dependencies)

## 対象プラットフォームと環境

CEFはLinuxのamd64・armhf・arm64、Windowsのi686・amd64を対象とする。Androidはarm64-v8a・x86_64を対象とする。デスクトップの公開ターゲット名は現在のmuon-uiと揃え、SDKではAndroidをandroid-arm64-v8a・android-x86_64として区別する。個々のプラグインは対応する対象を宣言し、アプリの要求した対象がなければビルド時にエラーとする。

LinuxはGCC、WindowsはMinGW、AndroidはNDKを標準とする。ホストと対象を区別し、pkg-configの探索先に別ターゲットのライブラリが混ざらないようにする。独自ビルドも同じヘッダー、定義、リンク情報を使用できるようにする。対象OS・CPUだけでなく、muonのプラグインABI、cardio、C++ランタイム、Android API下限などの条件を照合する。

現在のAndroidランタイムはNDK 29.0.14206865、minSdk 24、c++_sharedを使用する。依存.soも16 KiBページに対応する必要がある。Linux・Windows・Androidでcardioのコンパイル定義が異なるため、対応するランタイムと同じ定義・ヘッダー・リンク用ライブラリをSDKへ収録する。Windowsでネイティブコードからリンクする用途にはMinGW用インポートライブラリを提供する。

- [AndroidのC++ランタイム](https://developer.android.com/ndk/guides/cpp-support)
- [Androidの16 KiBページ対応](https://developer.android.com/guide/practices/page-sizes)

## 構成と責務

### 前提環境の診断に関する追加指示

開発者が不足する要素を容易にインストールできるよう、外部ツールチェインとライブラリの存在確認を強化する。作者向けの診断コマンドとビルド開始前の検査で、選択した言語・ビルド方式・ターゲットに必要なコンパイラ、Make・pkg-configまたは独自ビルドツール、NDKの指定バージョン、sysroot、SDKの対象別リンク入力、システム開発ライブラリを確認する。複数の不足はまとめて報告し、項目名、検出先、必要な条件、導入コマンドまたは公式導入文書を示す。ホスト用ライブラリの存在をクロスビルド対象の充足として扱わない。診断自体でツールをインストールしたりライセンスへ同意したりしない。ビルド済みプラグインを読むアプリ側には作者用ツールチェインを要求しない。存在する環境と不足する環境の両方をテストし、段階1・2の作者向け機能と段階5の利用文書に含める。

```text
sdk/
  package.json
  include/       公開C ABIヘッダー
  src/           CLI、ターゲット情報、成果物の検査・パッケージ化
  templates/     C/C++標準プロジェクト
  make/          標準Makefileの共通処理
  pkgconfig/     pkg-config設定
  cmake/         CMake Config package
  examples/      動作確認用アプリと使用例
  test/
```

公開C ABIヘッダーをsdk/includeで一元管理し、coreとbuilderもそこを参照する。cardioなどの外部ソースはdepsに保持し、改変しない。SDKの生成時に必要な配布ファイルを取り込む。アプリへの組み込みはui、実行時のロードはcoreが担当する。SDKの作者用CLIと、uiが利用する成果物の読込み・検査APIを分離し、パッケージ利用時にコンパイラを起動しない。

標準Makefile、C ABI用とC++・cardio用の.pc、CMake Config packageを提供する。ターゲット情報から共通の条件を生成し、ビルド方式ごとの手書きの重複を避ける。SDKのパスはNPMのインストール先へ追従し、作成時の絶対パスを配布物へ埋め込まない。独自ビルドの選択時は開発者の設定・コマンドを使う。

## ソース設定と共通成果物

ビルド設定には実装言語、ソース、標準・独自ビルド、対象、追加依存と出力先を記述する。独自ビルドの成果物もSDKの検査・包装処理に渡せるようにする。

共通の成果物メタデータには、スキーマ、プラグインABI、登録名、公開関数、対象別バイナリとハッシュ、実行時依存、公開ヘッダーとリンク情報、TypeScript型宣言を記述する。NPMパッケージ名・登録名・SONAMEを区別する。SDKとmuonの対応関係を検査し、初期段階から長期のバイナリ互換性を約束しない。

```text
muon-example-plugin/
  package.json
  muon-plugin.json
  include/
  types/
  native/<target>/
  licenses/
```

NPMパッケージはメタデータへの公開エントリーを持ち、Nodeのモジュール解決でパッケージを特定する。ビルド対象に従って成果物を選択し、NPMを実行するPCのOS・CPUで配布物を選別しない。ヘッダー・リンク用ファイルは開発時に使い、アプリへは実行時ファイルを収録する。

公開関数一覧と型宣言は当初は作者が用意し、SDKがstripなどの加工を終えたファイルのハッシュを生成する。現在のカタログは型シグネチャを含まないため、型宣言の自動生成や新しいIDLは今回必須にしない。カタログと実際の登録結果は動作確認で照合する。

## アプリへの統合と依存処理

ローカルプラグインは明示されたビルドを終えてからカタログを読み込み、Vite・CLIの処理へ渡す。独自ビルドにも同じ接続点を提供する。ビルド済みNPMパッケージはビルドせずに読み込む。CLIとViteで解決処理を共有する。権限とconfigはアプリが指定する。

プラグイン本体と通常の依存.so・.dllを区別する。現在のAndroid検査はすべての追加.soにmuon_init_pluginを要求するため、この制約を解消する。通常の依存ライブラリをプラグインとして登録しない。依存先の欠落、対象ABIの不一致、同名ライブラリの衝突、予約されたランタイムの差し替えを検査し、OSローダーが必要な依存を見つけられる配置にする。

CEFでも提供者の関数カタログを利用可能にし、Windows DLLなどをLinuxのビルドPC上で実行せずにアプリを構築する。既存の公開権限、配布時検査、実際の登録結果との照合を維持する。

## 実装段階と完了条件

### 段階1：SDKの独立した最小ビルド

SDK workspace、公開ヘッダーの一元化、ターゲット定義、リンク用成果物と.pcの生成、標準Makefileを実装する。C++20とcardioを使う最小プラグインをリポジトリ外でビルドし、既存muonアプリで呼び出せる成果物を作る。公開SDKはESM/CJSと型を提供し、TypeScript・Vite・Vitest、prettier-max・resolved-killer・screw-upを既存規則と公式文書に沿って設定する。

先に独立プロジェクトからSDKを利用するテストを追加して失敗を確認する。C/CEF・Androidの既存ビルドも公開ヘッダー移動後に成功し、対象別のコンパイルとリンクがリポジトリ参照なしで成功することを完了条件とする。

### 段階2：言語選択と独自ビルド、成果物形式

C99とC++20のテンプレート、CMake Config package、任意の明示されたビルドと既成成果物を扱うAPI・CLIを実装する。共通メタデータ、ヘッダー・型・ライセンスの収録、ハッシュ生成、対象とABIの検査を実装する。外部ソースは書き換えず、独立した出力先を使う。

MakefileとCMakeの両方でC/C++プラグインが生成でき、外部ソースを参照するサンプルと自作ソースだけのサンプルが同じ成果物形式で検証に成功することを完了条件とする。無効な成果物の拒否も振る舞いで確認する。

### 段階3：アプリからのローカル・NPM参照

ui共通処理へプラグインのソース・成果物・NPMパッケージの明示的な参照を接続する。ローカルビルド、カタログ読込み、Vite処理、アプリ生成の順序を共有する。CEFとAndroidのビルド・pack・開発時に反映し、提供者カタログをCEFでも利用する。型宣言を利用できる方法も整える。

npm packしたSDKとプラグインを新しいディレクトリへインストールし、元リポジトリとプラグイン用コンパイラを参照しないアプリの生成・呼出しが成功することを完了条件とする。ローカル専用プラグインはNPMパッケージ化なしで使用できることも確認する。

### 段階4：依存ライブラリとプラットフォーム横断の検証

通常の依存共有ライブラリの検査・同梱を実装し、CEF/Linuxの検索パス、WindowsのDLL解決、AndroidのELF・16 KiB・SONAME検査を接続する。cardioとC++ランタイムの整合を確認し、対象別リンク用成果物と配布用ランタイムを区別する。

ネイティブ依存を持つプラグインの呼出し、依存不足・同名衝突・不一致の拒否が成功することを完了条件とする。全対象の成果物をビルドし、Linux、Windows、AndroidでC/C++の関数呼出し、非同期処理、終了処理、カタログ不一致の拒否を確認する。Windowsは可能ならWineで検証し、Wine固有の問題ならagent-roverで実PCを使用する。Androidは両ABIの利用可能な実機・エミュレーターを使う。

### 段階5：外部作者向けの配布・文書・全体検証

SDKとプラグインの配布確認、独立サンプルとCI、利用者向け日本語文書を整え、必要な英語文書を日本語原本から更新する。SDKを本体の配布ビルドへ接続し、ヘッダー・インポートライブラリ・TS型・実行時バイナリの収録を確認する。

ルートの全体テストを最後まで実行し、SDKのテストと独立した利用者検証も実行する。四つの適用方法、C/C++、Makefile/CMake、CEF/Linux・WindowsとAndroidの結果を記録する。環境不足があれば具体的な不足を示し、必要な導入を促す。未検証項目を成功と扱わない。

## 作業方法と対象外

実装前に計画を保存してdoc:でコミットする。各段階は振る舞いの再現テストでREDを確認し、実装後にGREENを確認してfeat:・fix:・refactor:・chore:の適切な単位でコミットする。使われなくなった補助コードは残さず、既存コメントは内容に合わせて維持する。機能削除が必要な場合は削除を確認するテストでRED・GREENを確認して一度コミットした後、その一時テストも削除する。

SDKの開発基盤に必要な変更を対象とし、外部コードの変更、mainへのマージ、NPMレジストリへの公開、AAR・Java/Kotlin拡張、新しいIDL、不要な後方互換層は行わない。ブラウザー・muonを介する試行は利用可能なPlaywright MCPを使用する。問題が生じた場合は計画と設計の前提を見直し、場当たり的な修正を積み重ねない。
