# Node.jsサービスとCEF開発環境

## 目的と位置付け

CEFバックエンドでnative・QuickJS・Node.jsのサービスを選択できるようにする。同じサービス定義を配布ビルドと開発起動で使い、`muon run`と`vite dev`からサービスを含むアプリを実行できるようにする。`vite dev`ではサービスの変更を検出して再起動する。

本計画は2026年11月17日までの議論と、コミット`fc404cc4`のコードに基づく。[plan17](plan17.md)で保留したNode.jsサービスを扱い、CEFの開発起動を追加する。計画作成時点では実装を開始していない。

利用者が指定した対象範囲と追加回答を「合意済みの範囲」に記録する。それ以降の構成、再起動の単位、実装順序は議論で提示した設計案として保存する。設定キーなどの未確定事項は該当する実装段階で現在の規約と照合して具体化する。

## 用語

| 用語 | この計画での意味 |
| --- | --- |
| 論理サービス | `muon.json`の`services`へIDを付けて登録する実行単位 |
| サービスホスト | UIとは別のプロセスで、複数サービスの設定、参照、実行状態、通信を管理するプログラム |
| 実行世代 | サービスの起動ごとに区別する識別子。古い要求や応答を別の実行へ渡さないために使う |
| 利用者参照 | ページが`acquire()`で取得し、`release()`やページ破棄で解放する参照 |
| 常駐参照 | 自動起動設定がONの間、ホストがサービスごとに最大1つ保持する参照 |
| 開発セッション | 開発コマンドが管理するUI、サービスホスト、子プロセス、設定、配置先の組み合わせ |
| HMR | Viteがページ内のモジュールを更新する仕組み。ページ全体の再読み込みやサービスの再起動とは区別する |
| Node.jsサイドカー | muonから起動し、プロセス間通信で操作するNode.js子プロセス |

## 合意済みの範囲

| 項目 | 今回の対象 |
| --- | --- |
| CEFのサービス | Linux・Windowsでnative・QuickJS・Node.jsから選択できるようにする |
| Androidのサービス | native・QuickJSを維持する。Node.js指定はビルド時に拒否する |
| 開発起動 | CEFの`muon run`・`vite dev`でサービスも準備して実行する |
| 開発中の更新 | `vite dev`ではサービスの変更を検出して再起動する。画面だけのHMRを理由にサービスを再起動しない |
| 実行期間 | 現在と同じくエンドユーザーのセッション内とする |
| Androidの開発環境 | 現行のnative・QuickJSのビルド対応を維持する。端末への開発起動・更新は今回追加しない |

変更の反映方法について、利用者は「vite devでは変更を検出してサービスを再起動する」を選択した。画面だけの更新ではサービスを維持する前提も、この質問で共有した。

Androidの開発起動について、利用者は「今回はCEFの開発起動を整備し、Androidはnative／QuickJSのビルド対応を維持する」を選択した。

次の作業は今回の対象に含めない。

- systemdのsystem daemonやWindows Serviceとして動かす仕組み。
- QuickJS向けのファイルI/Oなど、基本機能を提供するオブジェクトの追加。
- `muon.server`の機能をサービスへ移す作業。
- executorや既存sidecar機能全体の再整理。
- AndroidのNode.jsサービスと、Android端末でのViteライブプレビュー。

Node.jsサービスを動かすために必要なプロセス起動・通信処理の再利用は行う。これを理由に、今回対象外とした機能の移動や全体設計の変更へ作業を広げない。

## 現在の実装

### 実装済みのサービス

nativeとQuickJSのサービスは、公開SDK、アプリへの組み込み、UIとの通信、配布まで実装されている。UIとは別のサービスホストが複数サービスを管理し、常駐参照があれば画面を閉じた後も処理を継続する。再表示したUIは同じ実行世代へ接続できる。

公開APIには取得・解放、メソッド呼び出し、キャンセル、呼び出し中のコールバック、イベント購読、状態取得・監視、自動起動設定の保存がある。64bit整数には`bigint`、バイナリーには`Uint8Array`を使う。状態監視は生存参照を増やさない。

QuickJSからはサービスごとに許可したnativeプラグインを呼び出せる。画面用の権限は継承しない。QuickJSにはDOM、Node.jsの組み込みAPI、`fetch`などを提供しておらず、I/Oは許可したnativeプラグインを利用する。この範囲は今回も維持する。

PCの常駐処理はユーザーセッションに依存する。Androidでは通知付きのforeground serviceとして実行し、OSの開始・継続制限に従う。Android API 30以降にはサービスホストの過去の終了を`lastHostExit`で取得する機能もある。これらの利用方法は[サービスガイド](../services.md)に記載されている。

### Node.jsを保留した理由

[既存の検証ドライバー](../../../node/test/service-host-probe.test.ts)では共通SDKをNode.js上で動かし、UIを模したプロセスの終了後に非同期処理とイベント通知が完了することを確認している。共通SDKを利用できないことが保留の理由ではない。

既存のページ用Node.js連携には、サービス用に変更すべき点がある。

- `createNode()`はページの所有者トークンを要求する。
- ページ用の公開方法はサービス側の関数単位の公開方法と異なる。
- 現在の`shutdown`を先に送ると、サービスの非同期停止が未完了でも子プロセスが終了する。
- WindowsのNode.jsプラグインはDLLをプロセス終了まで保持するため、サービス用プラグインプールへ移すだけでは解放の規約が合わない。

[サービスホストからの接続ドライバー](../../../core/cef-test/service-node-probe.test.ts)には、既存プラグインをそのまま接続した場合の失敗理由を観測する試験がある。本計画ではこれらをNode.jsサービスの実装と検証へ進める。

### 既存の検証範囲

[plan17の最終記録](plan17.md#2026年11月13日win11vmでの検証と最終判定)では、コミット`4626ce1`で全体の`npm test`が終了コード0で完了している。独立した配布アプリでもLinux amd64、Windows 32bit・64bit、Android実機・VMで動作を確認している。

Linux armhf・arm64は配布ビルドと依存関係の検査まで、Android arm64の16 KiB環境はバイナリーの整列検査までである。これらを実行確認済みとして扱わない。既存の成功記録は本計画で加える変更の検証を代替しない。

## Node.jsサービスの設計案

### 共通APIとプロセスの所有者

JS/TSのサービス定義にはQuickJSと同じ`defineService()`・`defineServiceInterface()`を使用する。画面側も`acquire()`、ハンドルの`call()`・`subscribe()`・`release()`を共通にし、必要に応じて`bindServiceClient()`で型を付ける。

サービスホストへNode.js用の実行アダプターを追加し、論理サービスごとにNode.js子プロセスを持つ構成を推奨する。サービスホストが子プロセスを所有し、サービスIDと実行世代へ結び付ける。これにより、サービスごとの作業ディレクトリと子プロセスの異常終了を分離できる。

既存の子プロセス起動、認証、通信の必要部分を再利用する。ページ用のNode.js連携をサービスの所有者として利用したり、ページ終了に合わせてサービスの子プロセスを終了させたりしない。必要な処理を共用する範囲はNode.jsサービスの実装に限定し、executor・sidecar全体の再整理へ広げない。

Node.jsサービスのエントリーとNode.jsプロジェクトはサービスごとに解決する。具体的な設定キー、パスの基準、公開型は段階3で確定する。`runtime: "node"`はCEFで受け入れ、Android向けでは対象サービスを示してビルド時に拒否する。

### 生存管理と通信

Node.jsにも既存の参照管理を適用する。利用者参照か常駐参照がある間は実行を必要とし、最後の参照の解放で停止へ進む。状態取得・監視は参照を増やさず、保存された自動起動設定を実行状態と区別する。

メソッド定義、値の検証、64bit整数、バイナリー、キャンセル、コールバック、イベントを共通SDKへ接続する。引数のコールバックは親メソッドの寿命に結び付け、継続的な通知にはイベントを使う。古い実行世代から届いた結果を、新しい世代の要求へ配送しない。

起動失敗、子プロセスの異常終了、通信断は、既存の失敗状態とハンドル無効化へ接続する。常駐設定がONという理由だけで失敗後の再起動を繰り返さず、通常の再取得と開発時の明示的な更新を区別する。

### 非同期停止

通常の停止は次の順序を満たすように実装する。

1. 新規要求の受付を止める。
2. 実行中の要求をキャンセルし、要求とコールバックの後片付けを待つ。
3. サービスの`stop()`を実行し、その非同期処理が完了するまで待つ。
4. Node.js側との通信を終了し、子プロセスの終了を確認する。
5. ホスト側の通信資源とプロセス資源を解放し、停止完了を通知する。

応答不能、停止期限超過、停止中の子プロセス異常終了も検証する。期限や失敗理由の具体的な表現は段階2で既存の規約と照合して決める。強制終了した場合は通常の停止完了と区別し、古い子プロセスや応答が次の実行へ残らないようにする。

## 配布と開発で共有する準備処理

### 共通処理の範囲

サービスの設定検証、ターゲット判定、ビルド、依存物の配置、ホスト用設定の生成を共通処理にまとめる。配布ビルド、`muon run`、`vite dev`は、この処理をそれぞれの配置先と起動方法へ接続する。

同じサービスを開発と配布で使うために、別々の定義を要求しない。サービスの準備に失敗した場合は診断を示し、不完全な構成でUIだけを起動して成功扱いにしない。

| 実装方式 | 準備する内容 |
| --- | --- |
| native | 対象OS・ABIのサービス成果物と依存ライブラリー。開発者がソースから作る場合はSDKのビルド設定も扱う |
| QuickJS | JS/TSエントリー、取り込むモジュール、許可したnativeプラグインを解決し、既存の実行環境向けにまとめる |
| Node.js | サービスのエントリー、TSの変換、Node.jsプロジェクト、npm依存、実行時アセット、実行用アダプターを準備する |

nativeのソースからのビルドには、SDKのビルド設定を明示的な入力として指定できる経路を追加する。ビルド済み`artifact`を使う経路も維持する。成果物だけを利用する場合は、その成果物の更新を監視する。

### Node.jsランタイムの準備

既存のNode.jsランタイム取得処理を利用し、Node.jsサービスだけを使うアプリでも必要なランタイムを準備する。ページ用Node.jsの設定の有無だけで、ランタイムの必要性を判定しない。

ページ用Node.jsと各サービスの`engines.node`、muon側の対応範囲を満たすランタイムを選択する方針を推奨する。条件が両立しない場合は、該当プロジェクトと条件を示してビルド時に拒否する。

配布物にはサービスの実行に必要なプロジェクト、依存物、アセット、アダプター、ランタイム要件を含める。開発元のソースや`node_modules`へ依存せず、移動した配布先から実行できることを検証する。Node.js実行ファイルの準備方法は、既存のランタイム取得方式へ接続する。

## CEFの開発セッション

### 起動と終了

開発コマンドがUI、サービスホスト、Node.js子プロセスをまとめて管理する。初期構成の準備が成功してからUIを起動し、途中で失敗した場合は、その起動で作成したプロセスと接続を回収する。

| 操作 | 設計案での動作 |
| --- | --- |
| `muon run`の開始 | サービスを準備し、ローカルのアセットと合わせて起動する |
| `vite dev`の開始 | サービスを準備し、Viteのページと合わせて起動する |
| UIのHMR | サービスをそのまま維持する |
| UIを閉じる | 通常の参照管理に従い、常駐参照があればサービスを継続する |
| ページ破棄・明示的な`release()` | そのページやハンドルの参照を解放する |
| 開発コマンド・Viteの終了 | サービスの停止を待ち、ホストとNode.js子プロセスも回収する |
| アプリ全体の明示終了 | UIとサービスを終了する |
| 起動途中の失敗 | 作成済みのプロセス、接続、途中の配置を回収する |

画面だけのHMRでサービスを維持することと、ページ破棄後もすべてのサービスを維持することは区別する。非常駐サービスの最後の参照がなくなれば、通常の規約に従って停止する。開発環境のために暗黙の常駐参照を追加しない。

現在のVite起動にはUI終了時にViteも閉じる`exitWithServer`の扱いがある。`muon run`もUIプロセスの終了を待っている。常駐サービスが継続する場合の開発コマンドの待機と、開発セッション全体を終了する操作を段階1で整合させる。

### 開発用の設定と配置先

開発用の接続先と保存領域は配布アプリから分離し、開発起動によってOSのログイン起動を登録しない方針を推奨する。プロジェクトや実行ターゲットを取り違えて既存ホストへ接続しないようにする。

開発セッション内の設定保存、UI再接続、既存のrecycleによるUI再起動も扱う。具体的な接続先の識別方法、保存領域の場所、既存オプションとの整合は段階1で決める。これらの内部情報を、サービス作者が手作業で指定しなければならない構成にはしない。

## Viteによる変更監視と再起動

### 監視対象と再起動の単位

サービスのエントリーだけでなく、取り込んだソース、設定、nativeのビルド入力・成果物など、実行結果を変える入力を監視する。生成先の`.muon`は監視から除外する。連続した編集は順序付けし、ビルドと再起動が重複して動かないようにする。

初期実装ではサービスホスト全体を再起動する案を推奨する。現在のnativeプラグインはサービス間で実行環境を共有しており、ホスト全体を単位にすると、DLLの解放と設定変更を一貫して扱える。[共有プラグインの管理](../../../core/common/src/services/muon_service_plugin_pool.cpp)を前提とする。

この案では変更対象以外のサービスもサービス更新時に再起動する。画面だけのHMRではホストを再起動しない。サービスごとの個別差し替えは初期実装の前提にしない。

### 更新の順序

1. 変更を検出し、現在使用中の配置先とは別の場所へ新しい構成をビルドする。
2. 設定、サービス、依存物の準備が成功したことを確認する。
3. 現在のサービスへ停止を要求し、非同期停止とホストの終了を待つ。
4. 新しい構成へ切り替え、サービスホストを起動する。
5. ページを再読み込みし、新しいハンドルを取得できるようにする。
6. 使用が終わった配置とプロセス資源を回収する。

使用中のDLLやJS成果物を上書きしない。旧ハンドルを新しい世代へ付け替えず、ページから取得し直す。更新のために保存済みの自動起動設定をOFF・ONへ書き換えない。

### 失敗時の扱い

ビルドに失敗した場合は現在のサービスを維持し、エラーを示す。監視を継続し、次の編集で再試行する。新しい構成のビルド成功と、サービスの起動成功は別々に判定する。

新しいサービスの起動失敗、停止期限超過、更新中の開発セッション終了も区別して扱う。起動失敗時の具体的な再試行・復旧方法は段階4で確定し、成功していない構成を実行中として表示しない。停止後に旧構成へ自動的に戻す仕組みは、現時点の合意事項には含まれない。

## 実装の順序

各段階で実行可能なドライバーまたはアプリを用意し、変更による動作を観測する。コードの変更は問題や不足を再現するテストのREDを確認してから実装し、GREENを確認する。段階ごとに適切な粒度でコミットする。

### 段階1 共通の準備処理と既存サービスの開発起動

サービスの設定検証、ビルド、配置、登録情報の生成を配布ビルドから共用できる形に整理し、`muon run`と`vite dev`へ接続する。この段階は既存のnative成果物とQuickJSを対象にし、Node.jsや変更監視の完成を待たずに実行できるようにする。

開発用の接続先と保存領域、UI終了と開発セッション終了の違い、`exitWithServer`とrecycleの扱いも実装する。起動失敗と開発終了時の回収を含めて検証する。

成果物は同じnative・QuickJSサービスを配布ビルド、`muon run`、`vite dev`で利用できるアプリとテストである。

```json
    "worker": {
      "runtime": "node",
      "project": "./worker",
      "entry": "./src/service.ts",
      "autostart": true
    }
  }
}
```

サービスのTSはViteでESモジュールへ変換する。モジュールのディレクトリ構成を保ち、プロジェクトのアセットも配置するため、`import.meta.url`を基準にしたファイル読み込みを利用できる。Node.jsの組み込みAPIとnpmパッケージはNode.js側で解決する。

npm依存はインストール済みのものを配置する。実行時の依存と間接依存、ソースから取り込む外部パッケージを対象とし、必須の依存がなければ`npm install`を案内して準備を失敗させる。静的な`import`に必要なパッケージの不足も検出する。任意の依存物を動的に読み込み、見つからなければサービス自身が代替処理を選ぶ動作は維持する。準備処理からインストールやパッケージのスクリプトを実行しない。複数パッケージで共有していた同じ依存物が配置後に別のインスタンスになる問題をテストで再現し、共有関係を保つ配置へ修正した。

ページ用Node.js、各サービス、muonブリッジのすべてが受け入れるランタイム条件を求める。条件が両立しない場合は、プロジェクトのパスと`engines.node`を示してランタイム準備前に拒否する。サービス用のプロジェクトも出力先の削除やUIアセットへの混入を防ぐ事前チェックの対象にした。

公開SDKには[node-files.ts](../../../sdk/examples/services/node-files.ts)と隣接するアセットを追加した。このサンプルは共通SDKでメソッドを定義し、Node.jsのファイルAPIでアセットを読む。停止時にはサービス専用のデータ領域への保存完了を待つ。同じサンプルを開発起動と配布先の実ホストで検証した。

### 2026年11月17日 段階4の変更監視とサービス更新

nativeサービスの`source`にSDKのビルド設定を指定できるようにした。`artifact`と`source`のどちらか一方を使い、ソースからビルドする場合は`sysroot`も指定できる。パスは`muon.json`のディレクトリを基準に解決する。例えば`{"runtime":"native","source":"./worker/muon-plugin.build.json"}`で、開発起動と配布ビルドのどちらからも同じソースを使える。

ビルド先はアプリ側の`.muon/service-build`とし、サービス作者のディレクトリへ生成物を書き込まない。ファクトリー名などの設定を変更した場合は別の出力先を使う。ビルド済み`artifact`だけを利用する経路も維持した。

Viteではサービスの入力を画面のHMRと区別して監視する。監視する入力は次のとおりである。

| 実装方式 | 監視する入力 |
| --- | --- |
| 共通 | `muon.json`などのアプリ設定。サービスとNode.jsの設定に変更がなければ、設定ファイルの変更だけではサービスを再起動しない |
| nativeのソース | SDKビルド設定、宣言したソース・ヘッダー、ビルド用ディレクトリ、SDKのヘッダーとビルド資材、明示したツール、`dependencies`・`linkLibraries`の入力 |
| nativeの成果物 | 成果物のマニフェスト、使用するターゲットのライブラリーと依存物 |
| QuickJS | 読み込んだモジュール、相対importの未解決先、設定ファイル、許可したnativeプラグインの入力 |
| Node.js | プロジェクトのソースとアセット、設定ファイル、配置するnpm依存。`node_modules`内の依存も監視する |

生成先の`.muon`とGitの管理領域は監視から除外する。サービスホスト全体を更新の単位とし、変更対象以外のサービスも再起動する。次の構成を別の配置先へ準備してから、現在のサービスの非同期停止とホスト終了を待つ。新しいホストの起動確認後にページを再読み込みし、新しいハンドルを取得できるようにした。Node.jsのランタイム要件が変わる場合はランタイムも別の場所へ準備し、UIを再起動する。

ビルドや配置に失敗した場合は旧サービスを維持する。起動や停止の失敗は診断を表示し、次の編集で更新を再試行できる。失敗したビルドで見つけた入力も監視に残すため、不足する依存ファイルを作成するだけで再試行できる。旧ハンドルは無効なままとし、保存済みの自動起動設定を保つ。開発終了時には進行中の準備を待って、サービス、配置先、ファイル監視を回収する。

次の不具合は失敗するテストを確認してから修正した。

- nativeの外部依存ライブラリーの更新を検出できない。
- 監視開始中にViteを終了してもファイル監視が残る。
- 非同期停止の作者エラーを成功扱いする。
- サービス更新後にUIの自動起動設定を取得できない。

UIの設定操作には新しい接続を使えるようにしたが、古いサービスハンドルを新しいホストへ付け替える処理は加えていない。

監視対象の親子ディレクトリを重複して走査すると、既存ファイルを追加と誤認する問題も修正した。配布用JSのビルドでは監視ライブラリーを外部依存として扱い、Node.js向けのESM・CJSから利用できるようにした。
