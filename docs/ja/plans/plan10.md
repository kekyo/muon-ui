# Linux向けAppImageとビルド時の共有ライブラリ要件判定

## 目的と合意した方針

Linux向けの配布形式にAppImageを追加する。CEFは既存のdebと同様に実行時に取得し、ユーザーが書き込める場所へ実行環境を準備する。配布物へCEFを同梱する方式は今回の対象に含めない。

共有ライブラリの最低要件は、muonのビルドに使用するCEFを基準に算出する。実行時のCEF選択に`tested`以外が指定されていても、同じビルド時の参照CEFを使用する。将来ダウンロードされるCEFごとの厳密な最低バージョン特定、実行時の追加ABI検査、候補CEFの除外や自動フォールバックは追加しない。既存のCEF選択ポリシーとAPI互換性の判定は維持する。

CEFを基準として古い共有ライブラリを使用できるよう、muon側のビルド環境も調整する。ただし、muon本体やプラグインが必要とする条件をCEFの条件で上書きしてはならない。配布物全体に必要なライブラリの条件を求め、その条件を満たす基準環境でビルドと実行を確認する。

本書には、AppImageの追加、Electronアプリとの比較、共有ライブラリの調査結果、ビルド時の要件判定についての議論を保存する。当初の調査時点は2026年10月15日、コードの基準は`95dc2712`である。実装開始後の結果は末尾の実施記録へ追記する。

## CEFのバージョン選択と取得時期

CEFのバージョンを決める時期、CEFをダウンロードする時期、配布物へCEFを収録するかどうかは別の選択である。ビルド時に参照CEFを決めても、利用者の環境で初めてダウンロードする構成にできる。

現在の`tested`は、ビルド時に記録した参照CEFを実行時に取得する。`same-major-latest`と`compat-latest`では、参照CEFのAPIハッシュと互換性がある候補を実行時に選択する。特定バージョンを指定する経路もある。APIハッシュによる判定は、OS側の共有ライブラリの互換性まで保証するものではない。

| 検討した構成 | 配布物と実行時の処理 | 今回の扱い |
| --- | --- | --- |
| 参照CEFを実行時に取得 | 小さい配布物から起動し、初回にCEFを取得する。`tested`が該当する。 | 採用する。 |
| API互換性のあるCEFを実行時に選択・取得 | 既存の選択ポリシーで取得する。最低ライブラリ要件の算出にはビルド時の参照CEFを使う。 | 採用する。 |
| 固定CEFを配布物へ同梱 | 配布サイズは増えるが、CEFの初回ダウンロードは不要になる。 | 比較結果を記録し、今回の実装からは外す。 |

CEFを同梱すればCEFの取得通信を省けるが、Node.jsなど別の実行時依存まで自動的に不要になるわけではない。また、CEFを同梱するだけではOS側のABIやドライバの互換性は解決しない。

当初の検討では、将来選択するCEFの最低要件も検査する案を挙げた。その後の指示に従い、今回の依存要件の算出はビルド時の参照CEFに限定する。実行時に選ばれた別のCEFが異なるOS要件を持つ可能性は残るが、その差を厳密に追跡する機能は実装しない。

既存のユーザー単位の起動では、`XDG_STATE_HOME`または`~/.local/state`の下にある`<app-id>/runtime`へ実行環境を準備する。CEFの取得キャッシュは別に管理する。この配置を利用すれば、配布元が読み取り専用でも起動時の取得と準備を行える。

現在の`tar.gz`は`type: portable`、`runtimeMode: in-place`で、展開先に書き込む方式である。その設定をAppImageへそのまま流用すると、読み取り専用のマウント内へ書き込もうとする。AppImageはユーザーの状態ディレクトリを使う起動方式として扱う。

準備処理は、配置元にあるCEFの共有ライブラリやリソース、生成済みの準備状態、`runtimes`などをmuon本体のコピーから除外する。したがって、既存のdistへCEFを置くだけでは同梱方式にならない。同梱を採用するなら専用の準備経路が必要になるが、今回その変更は行わない。

## AppImageとElectronアプリの比較

AppImageは配布形式であり、Linuxの実行環境全体を仮想化するものではない。AppDirというディレクトリへアプリ、必要なライブラリ、起動用の`AppRun`、デスクトップ情報、アイコンを配置し、それをファイルシステムイメージにする。起動時にはAppImage側の起動プログラムがイメージを扱う。この起動プログラムとCEF runtimeは別のものである。[AppDir仕様](https://docs.appimage.org/reference/appdir.html)

広いLinux環境で動作させるには、対応する最古の基準環境に合わせてバイナリを作り、基準環境に存在しない依存物を必要に応じて同梱する。AppImageへ変換しただけで新しいglibcへの要求が消えることはない。[AppImageのビルド上の推奨事項](https://docs.appimage.org/reference/best-practices.html)

ElectronはChromiumとNode.jsを含む実行環境をアプリとともに配布する。CEFを使うmuonとは構成が異なり、利用者の起動時に任意のCEFを選ぶ構成ではない。このため、配布時点のChromiumを前提に依存関係を検証できる。[Electronの構成](https://www.electronjs.org/docs/latest/)

### EffeTuneの配布物で確認した内容

[EffeTune v2.13.0のLinux配布物](https://github.com/Frieve-A/effetune/releases/tag/v2.13.0)を展開し、`EffeTune-2.13.0.AppImage`の内容とELFの依存情報を静的に調べた。調査対象の配布ZIPのSHA-256は`fa4c854e57a9e8d5df7118de98f24f89fce4420b6e122142b1b70c7da53ee55d`である。これはその配布物の調査結果であり、すべてのElectronアプリへ一般化しない。

| 確認対象 | 結果 |
| --- | --- |
| CPU | x86_64向けの単一ファイルだった。すべてのCPUで使える共通バイナリという意味ではない。 |
| 同梱ライブラリ | Electron側の`libffmpeg.so`、Vulkan関連ライブラリなどに加え、`usr/lib`に`libXss.so.1`、`libXtst.so.6`、`libappindicator.so.1`、`libgconf-2.so.4`、`libindicator.so.7`、`libnotify.so.4`があった。OpenHome用のlibnlも含まれていた。 |
| ホスト側への依存 | Electronの実行ファイルはGTK、GLib、NSS、NSPR、X11、GBM、ALSAなどを要求していた。これらすべてをAppImage内へ収録する構成ではなかった。 |
| 補助プログラム | OpenHome用の補助プログラムに`GLIBC_2.34`と`GLIBCXX_3.4.32`への要求があった。アプリ本体以外からも実行環境の下限が決まる。 |
| sandbox | `AppRun`は`unshare -Ur true`でuser namespaceを試し、失敗時に`--no-sandbox`を追加する処理を持っていた。 |

EffeTuneの例から確認できたのは、必要なものを一部同梱し、残りをホスト環境に求める配布方法である。共有ライブラリの互換性をすべて解決しているとは言えず、配布物内の補助プログラムに高い要件が残る場合もある。今回の調査では配布物の構成と要求シンボルを確認しており、各ディストリビューションでの動作を実証したわけではない。

sandboxの回避処理も、共有ライブラリの互換性を解決する処理ではない。user namespaceの利用可否はホスト設定に依存する。[AppImageのElectron sandboxに関する説明](https://docs.appimage.org/user-guide/troubleshooting/electron-sandboxing.html)

muonでも、ホストに求める条件と同梱するライブラリを定める方式を採る。CEFを実行時に取得する点は維持し、依存要件の算出にはビルド時の参照CEFを使用する。

## 共有ライブラリの最低要件の調査結果

共有ライブラリとのバイナリ上の接続条件をABIと呼ぶ。ABIの検査では、要求するライブラリ名と、そのライブラリから使用する関数・データ名を確認する。ELFに記録された`SONAME`はライブラリの識別名であり、`libglib-2.0.so.0`の末尾だけからGLibの最低リリースを判断することはできない。

glibcなどには、関数・データに付けたシンボルバージョンもある。`GLIBC_2.34`はglibc側の要求を表し、`GLIBCXX_3.4.29`はlibstdc++側のABI名である。後者をlibstdc++パッケージのリリース番号として扱わない。

### 現在の成果物の実測

参照CEFのLinux minimal配布物と、現在の`ui/dist/runtime`および`ui/dist/native`にある成果物を`readelf`で調べた。次の表は要求側のシンボルバージョンの最大値である。提供側のバージョン定義とは区別して集計した。

| 対象 | GLIBC | GLIBCXX | CXXABI | 調査対象 |
| --- | --- | --- | --- | --- |
| CEFの`libcef.so` | 2.17 | 未検出 | 未検出 | amd64・armhf・arm64 |
| `muon-core` | 2.34 | 3.4.29 | 1.3.13 | amd64・armhf・arm64 |
| `libmuon-ui.so` | 2.32 | 3.4.29 | 1.3.9 | amd64・armhf・arm64 |
| executorのsupervisor | 2.34 | 3.4.29 | 1.3.9 | amd64・armhf・arm64 |
| `muon-launcher`、プラグイン検査器 | 2.34 | 未検出 | 未検出 | amd64 |

CEFの`libcef.so`には`NSS_3.30`への要求もあった。`libcardio`のGLIBC要求はamd64で2.3、armhfで2.4、arm64で2.17だった。CEFに付属するEGL、GLES、Vulkanなどのライブラリも個別に調べる必要がある。

`muon-core`では`dlopen`、`dlsym`、`__libc_start_main`などが`GLIBC_2.34`を要求し、`libmuon-ui.so`では`__libc_single_threaded`が`GLIBC_2.32`を要求していた。CEFの`libcef.so`だけを基準にglibc 2.17対応と表示することはできない。下限を下げるには、muon側の成果物を古い基準環境で作り直し、要求が変わったことを確認する。

この表は調査時の成果物に対する静的解析であり、対応OSの確定表ではない。同梱ライブラリの依存先、実行中に読み込むライブラリ、カーネルや描画環境の条件まで満たしたかは別途確認する。

### Debianのパッケージバージョンへの変換

Debian系の`dpkg-shlibdeps`は、使用シンボルとパッケージの`symbols`情報を照合し、必要な最低パッケージバージョンを計算する。シンボル単位の情報がない場合は、ライブラリ単位の`shlibs`情報を使う。[dpkg-shlibdeps](https://manpages.debian.org/bookworm/dpkg-dev/dpkg-shlibdeps.1.en.html)、[symbols形式](https://manpages.debian.org/bookworm/dpkg-dev/deb-symbols.5.en.html)

既存のbookwormコンテナで参照CEFの`libcef.so`を解析すると、例えば次の条件が得られた。

```text
libglib2.0-0 (>= 2.39.4)
libnss3 (>= 2:3.30)
libgbm1 (>= 21.1.0)
libasound2 (>= 1.0.17)
libdbus-1-3 (>= 1.9.14)
```

同じ解析では`libc6 (>= 2.34)`も出力された。これはELFのGLIBC要求の最大値2.17とは異なる。パッケージ依存の計算には、解析環境でのシンボルの提供元とパッケージメタデータも影響するためである。今回の出力だけからCEF本来のglibc下限を2.34と確定しない。

`dpkg-shlibdeps`の結果は対象環境のパッケージ情報に依存し、`shlibs`などから保守的な下限になる場合がある。開発PCのライブラリを偶然参照することを避け、対象CPUと基準ディストリビューションを固定して解析する。Debianのパッケージ名やepochを含む版番号を、他のディストリビューションへそのまま転用しない。

解析ではCEFの`libpthread.so.0`と`libdl.so.2`に対する未使用リンクの警告も出た。解析自体は成功したが、警告の内容は保持し、外部のCEFバイナリを改変して解消しない。

## ビルド時に行う抽出と決定

### 解析入力と記録する情報

解析入力には、ビルド時に取得した対象CPU用CEFと、完成したmuon本体、launcher、補助プログラム、プラグイン、同梱する共有ライブラリを含める。Node.jsを含む構成では、実際に検証するNode.jsにも独立した要件がある。CEFの要件だけでNode.jsの動作を保証しない。

参照CEFのバージョン、対象CPU、配布物を識別するハッシュ、基準環境、解析ツールとパッケージ情報の出所を記録する。ライブラリごとに、依存名、必要なシンボルとシンボルバージョン、対応する最低パッケージバージョン、要求元の成果物、同梱とホスト依存の区分を保持する。

この共通メタデータをmuonの対象別ランタイム成果物にも含め、NPM配布物からアプリをpackするときにも参照できるようにする。利用アプリのpackで、依存解析のためだけにCEF一式を再取得する構成は避ける。アプリ固有のプラグインや依存物を追加した場合は、その要求も合成する。

### ELFからの抽出

最低限、次の情報を取得する。

```sh
readelf -W -d libcef.so
readelf -W --version-info libcef.so
readelf -W --dyn-syms libcef.so
```

`DT_NEEDED`から直接の依存ライブラリを、バージョン要求情報から外部への要求を、動的シンボル表から必要な関数・データを取り出す。提供側のバージョン定義を要求として数えない。弱い参照は必須の参照と区別する。最大バージョンは報告用に使い、検査には必要なシンボルの集合を使用する。[readelf](https://sourceware.org/binutils/docs/binutils/readelf.html)

各共有ライブラリがさらに要求する依存も調べる。対象バイナリを実行する必要のない解析を使い、ホストと異なるCPUのELFも対象とする。`dlopen`や`dlsym`による条件付きの読込みは、コードと上流の情報から必要な宣言を補い、実行テストで確かめる。ファイル名やバージョン文字列の検索だけで完全な依存関係を求めたことにしない。

### 基準環境とビルド条件の選択

対象環境のヘッダーとライブラリをまとめたディレクトリをsysrootと呼ぶ。古い環境への対応では、基準とするコンテナまたはsysrootを固定し、その環境へ向けてmuonをビルドする。コンパイラの新しさと、実行時ライブラリへの最低要求は分けて扱う。

まず参照CEFが必要とするライブラリの条件を求め、対応候補の基準環境に含まれるライブラリと照合する。次に同じ基準環境へ向けてmuon本体と同梱物をビルドし、完成した成果物の要求を再解析する。CEFとmuonの両方を満たす組み合わせを採用し、依存ライブラリの版番号を個別に下げるだけの調整は行わない。

C++20を使用できるコンパイラと、必要なlibstdc++の条件も確認する。完成済みバイナリの要求シンボルを付け替えたり、依存メタデータの下限だけを書き換えたりして古い環境への対応を装わない。具体的な基準ディストリビューションとパッケージ版は、段階1・2の抽出、ビルド、実行結果で決定する。

ChromiumもLinuxビルドにsysrootを使い、パッケージ依存の計算結果を対応ディストリビューションの版と照合する処理を持つ。この方法を参考にし、muonでもビルド時の要件判定を行う。[Chromiumのsysroot](https://github.com/chromium/chromium/blob/147.0.7727.138/docs/linux/sysroot.md)、[Chromiumの依存検査](https://github.com/chromium/chromium/blob/147.0.7727.138/chrome/installer/linux/debian/calculate_package_deps.py)

### debとAppImageへの反映

debでは共通の解析結果から最低バージョン付きの依存情報を生成する。現在のt64移行前後のパッケージ名の扱いを確認し、対象CPUとABIに合う条件を付ける。静的解析に現れない実行時依存の宣言も合わせて保持する。

AppImageでは、基準環境に存在するものをホスト依存とし、それ以外で同梱するものを明示する。glibcや動的ローダー、GPUドライバなどを無条件に収集して同梱する方式は採らない。同梱したライブラリについても、そのライブラリ自身の要求を検査する。

CEF本体をAppImageへ入れないため、AppDirのELFだけを走査する通常の依存収集ではCEF側の依存を見落とす。ビルド時に生成したCEFの依存情報を収集処理へ加え、後から取得するCEFが使う共有ライブラリも含めて配置を決める。

共有ライブラリの取得元、バージョン、再配布するファイルと必要なライセンス情報を記録する。基準環境にないシンボルやライブラリを要求する成果物ができた場合は、要求元を示してビルドまたはpackを失敗させる。この検査のCEF入力は、実行時の選択ポリシーにかかわらずビルド時の参照CEFとする。

## AppImageの起動と利用者から見た動作

### 配布形式と対象

公開の配布形式に`appimage`を追加し、CLIとVite・APIの共通pack処理から生成できるようにする。対象は既存のLinux amd64・armhf・arm64で、CPUごとに別のAppImageを生成する。WindowsとAndroidに対する選択は既存の形式検査に従って拒否する。

形式を省略した場合の「選択ターゲットで利用できる形式を生成する」という既存方針へAppImageを追加する。AppImage生成ツールのバージョンと対象CPU用の起動プログラムを固定し、必要なツールがない場合は名前と導入方法を表示する。

### 読み取り専用の配置と状態の保存

AppDirには`AppRun`、デスクトップファイル、アイコン、muonの配布元ファイル、同梱する共有ライブラリを置く。AppImage内部へCEF、Node.js、プロファイル、キャッシュ、ログや準備状態を書き込まない。CEFと必要に応じたNode.jsの取得・キャッシュ・準備は既存の処理を再利用する。

`AppRun`からlauncherへ起動をつなぎ、ユーザーの状態ディレクトリへ実行環境を準備する。同梱する通常の共有ライブラリについては、launcher自身の起動と、準備後のmuon・CEFの起動の両方で探索できる配置にする。準備処理によって必要な依存物が脱落したり、終了済みのAppImageのマウント先へ依存したりしないことを確認する。

初回に必要なCEFがなければ従来どおりダウンロードし、利用可能なキャッシュがあれば再利用する。通信が必要な条件とキャッシュで起動できる条件は、既存のポリシーと取得処理に合わせる。AppImageであることを理由に、CEFの版を固定したり別のポリシーへ変更したりしない。

### メニューと自動起動

AppImage起動時には、`APPIMAGE`から配布されたAppImageの絶対パス、`APPDIR`から現在のマウント先を取得できる。永続化する再起動先には元のAppImageを使用する。[AppImageの環境変数](https://docs.appimage.org/packaging-guide/environment-variables.html)

デスクトップエントリと自動起動に、毎回変わるマウント先や一時展開先を記録しない。launcherとcoreの間で元のAppImageの起動先を共有する。アイコンなど永続的に参照するファイルも、終了後に消えるマウント先だけへ依存させない。

空白や日本語を含むパス、引数の受け渡し、AppImageを移動した後の再起動を確認する。移動後にAppImageを直接起動した際は、muonが管理する登録先を現在の配置に更新する。AppImageの自動更新機能は追加しない。

### sandboxとFUSE

現在の`--linux-sandbox=setuid`はdeb専用で、root所有の補助プログラムとシステム領域を利用する。AppImageでは通常起動の既存設定を使用し、setuid指定は非対応としてpack時に報告する。AppImageのために管理者権限でホストを変更したり、sandboxの自動切替を新設したりしない。

FUSEはAppImageのイメージを扱うためのホスト機能であり、CEFの共有ライブラリの問題とは分けて扱う。選択したAppImage起動プログラムで通常起動と展開実行を検証し、FUSEが使えない場合の実行方法を利用文書へ記載する。展開実行でも元のAppImageパスが取得できる場合は、再起動先にそれを使用する。[FUSEと展開実行](https://docs.appimage.org/user-guide/troubleshooting/fuse.html)

## 実装段階と各段階の完了条件

### 段階1　参照CEFと既存成果物の依存解析

ビルド時の参照CEFと既存のLinux成果物から、依存名、必要なシンボル、最低パッケージバージョン、要求元を取得する処理を追加する。対象CPUと基準環境を明示し、解析結果を人が読める報告と共通メタデータとして出力する。既存アプリのビルドと実行は維持する。

必要なシンボルを提供する場合と不足する場合を、実際のELFを使って検査するテストを先に追加し、REDを確認する。実装後には両者を正しく区別できることを確認する。同じ参照CEFに対して実行時ポリシーだけを変更しても、依存要件の算出結果が変わらないことを検証する。

完了条件は、Linuxの3対象の解析結果を取得でき、現在のmuon側の高い要求を発生元まで説明できることとする。未解析の依存を黙って除外せず、静的に確定できない項目はその旨を報告する。

### 段階2　基準環境の調整とdebへの反映

参照CEFの要件から基準環境を選び、muon本体、launcher、補助プログラム、共有ライブラリをその環境へ向けてビルドする。完成した成果物の要求を再解析し、基準環境との一致を検査する。共通メタデータを対象別ランタイムへ収録し、debの最低バージョン付き依存情報を生成する。

不足するライブラリ・シンボルの拒否、複数の成果物からの要求の合成、debの依存解決を振る舞いとして検証する。パッケージ名の文字列がソースに存在することだけをテストしない。基準環境で既存のサンプルアプリを起動し、CEFを実行時に取得して表示できる成果物を作る。

完了条件は、3対象のビルドが成功し、採用した最低要件の根拠が記録され、生成したdebが対象環境で依存を解決できることとする。低い要件でのビルドが成立しない場合は、必要な機能とビルド環境を調べ、条件を偽って先へ進めない。

### 段階3　起動できるAppImageの生成

`appimage`の型、CLI、対象判定、AppDir生成、`AppRun`、AppImage生成ツールの呼出しを実装する。まずamd64で、実行時CEF取得とユーザー領域への準備を利用するAppImageを生成する。参照CEFの依存情報を使い、必要な同梱ライブラリを収録する。

読み取り専用の配置元からの起動が失敗するテストを先に用意し、AppImageの起動経路を実装してGREENにする。空の状態ディレクトリからの初回起動、既存キャッシュを使った再起動、取得が必要な状態での通信失敗と再試行を確認する。

完了条件は、単一のAppImageから既存サンプルの画面を表示でき、CEFの取得・状態保存をマウント外で行えることとする。既存仕様でオフライン起動できるキャッシュ条件も確認する。CEFの同梱や実行時ポリシーの変更でテストを通さない。

### 段階4　デスクトップ連携とLinux全対象

メニュー、自動起動、永続的なアイコン参照、移動後の再登録をAppImageの起動先へ接続する。setuid指定の拒否、FUSEを利用する通常起動と展開実行、通常の共有依存を持つプラグイン、Node.jsを使用するアプリの起動を確認する。armhf・arm64にもAppImage生成を接続する。

終了してマウントがなくなった後のメニュー・自動起動、空白や日本語を含むパス、同梱ライブラリの探索を実際の起動で検証する。実行時に`tested`以外を指定した場合も、選択ポリシーが維持され、依存解析の基準がビルド時のCEFであることを確認する。将来のCEFすべての互換性検証を完了条件にはしない。

完了条件は、3対象のAppImageを生成でき、各対象で利用可能な実行環境により起動とライブラリ解決を確認できることとする。静的解析や別CPUでの生成だけを、そのCPUでの実行成功として記録しない。

### 段階5　配布・利用文書・全体検証

NPM配布物からのAppImage生成、CI、ツールの準備、基準環境と依存メタデータの再生成を接続する。日本語の利用文書に作成方法、対象CPU、初回取得、状態の保存先、ホスト側の要件、FUSE、sandboxの扱いを記載し、必要な英語文書を日本語原本から更新する。

既存のdeb・tar.gzなどの配布とCEF選択の回帰を確認する。基準環境と、対応を表明する別のLinux環境で起動、描画、音声、プラグイン、必要に応じたNode.jsを検証する。ブラウザ・muonを介する試行にはPlaywright MCPを使用する。

最後にルートの`npm test`による全体テストを完走する。タイムアウトした場合は処理の進行と所要時間を確認し、必要なら時間制限を調整する。環境不足と未検証項目を具体的に記録し、全体テストや対象別検証を省略した状態を完了扱いにしない。

## 作業方法と対象外

計画書は`doc:`でコミットし、実装は上記の段階ごとに適切な粒度でコミットする。実装前に振る舞いのテストでREDを確認し、実装後にGREENを確認する。機能削除が必要になった場合はプロジェクトの削除手順に従う。使われなくなった補助コードは残さず、既存コメントは内容に合わせて維持する。

新しい解析処理は既存のビルド構成に合わせ、自由にスクリプトを選ぶ箇所ではNode.jsを使用する。ビルド時のテキスト処理にはfuncityを使用する。外部ツールの使用方法は公式文書と該当API・実装コメントで確認する。外部のCEF、AppImage関連ツール、その他のベンダーコードは変更しない。

必要なビルド・テスト用パッケージが不足し、導入に管理者権限が必要な場合は、具体的なパッケージ名と導入方法を示す。ビルドの警告は発生元と意味を調べ、未分析のまま残さない。実装中に新しい問題が判明した場合は計画の前提を見直し、不要になった対処を積み重ねない。

今回の対象外は、CEF同梱によるオフライン初回起動、実行時CEFごとの厳密なOS依存検査、CEF選択ポリシーの変更、AppImageの自動更新、ホストの管理者設定の自動変更である。mainへのマージや外部への公開は、この計画の保存・実装だけでは行わない。

計画書を保存した段階では、文書の内容、参照先、差分を確認した。上記の全体テストは実装完了時に行う。

## 実施記録

### 段階1　依存解析の追加

参照CEFとmuonの成果物を静的に解析するコマンドを追加した。参照CEFは対象別の`CMakeCache.txt`から読み、アプリの実行時ポリシーは解析入力に含めない。`readelf`で要求シンボルと提供シンボルを区別し、依存先を再帰的に照合する。ライブラリ探索には明示した基準環境だけを使う。

`npm run build:linux-dependencies --workspace muon-ui`でコマンドをビルドできる。実行には`--target`、`--cmake-cache`、`--cef`、`--runtime`、`--output`を指定し、launcherなどを別のディレクトリで管理している場合は`--native`も指定する。JSONの共通メタデータと、要求元別のシンボルバージョン、Debian依存条件、診断を含むテキストを出力する。CEFの版とアーカイブの検証済みハッシュ、各ELFのSHA-256、基準環境のパッケージ一覧、解析ツールの版を記録する。

既存のbookwormコンテナで、amd64・armhf・arm64の各対象について115個のELFからなる依存関係を解析し、必須シンボルの不足がないことを確認した。各対象の報告は`core/cef/.build/plan10-dependencies/`に生成した。これは変更前の基準環境の測定値であり、古い環境での動作確認を意味しない。

| 要求 | 発生元と根拠 |
| --- | --- |
| GLIBC 2.34 | muon-core、executorのsupervisor、launcher、プラグイン検査器など。 |
| GLIBCXX 3.4.29、CXXABI 1.3.13 | muon-coreとNodeプラグインなど。Debianの依存条件は`libstdc++6 (>= 11)`。 |
| GLibパッケージ2.73.2以降 | muon-coreのファイル操作。`g_file_make_symbolic_link_async`と完了処理を使用する。安定版APIとしてはGLib 2.74で追加された。[GIOのAPI文書](https://docs.gtk.org/gio/method.File.make_symbolic_link_async.html) |
| libffi 3.4以降 | muon-coreが`LIBFFI_BASE_8.0`、`LIBFFI_CLOSURE_8.0`を要求する。 |
| GBMパッケージ21.1.0以降、NSSパッケージ3.30以降 | 参照CEFからの要求。NSSのDebian版番号にはepochの`2:`が付く。 |

CEFの未使用リンクに関する`libpthread`と`libdl`の警告は、glibc 2.34以降でこれらの機能がlibcへ統合された環境で発生している。診断を報告に保持し、CEFバイナリは変更していない。[glibc 2.34の変更内容](https://sourceware.org/pipermail/libc-announce/2021/000032.html)

armhfでは、`dpkg-shlibdeps`が`__aeabi_atexit@CXXABI_ARM_1.3.3`を未解決として警告した。静的解析では`libstdc++.so.6.0.30`の提供シンボルと一致している。dpkg側には`__aeabi_`を内部シンボルとして除外する処理があるため、この診断と実際のシンボル照合結果を区別する。警告は削除せず記録する。[dpkgの該当ソース](https://sources.debian.org/src/dpkg/1.21.22/scripts/Dpkg/Shlibs/SymbolFile.pm/)

実際にコンパイルしたELFを使う10件のテストで、必須シンボル不足、弱い参照、推移的な依存、CPU不一致、最低パッケージ条件、実行時CEFポリシーからの独立性を確認した。同じ版ノードを持つライブラリでも必要な関数がなければ拒否する。解析時の一時パスを配布用メタデータへ残さないことも確認した。

この段階ではELFの静的依存を解析している。`dlopen`で条件付きに使う外部ライブラリ、描画ドライバ、カーネル機能の網羅的な動作確認は未実施であり、後続段階の宣言と実行試験で補う。
