# Origin-based permissions (Advanced topics)

You may think that any cloud service can be used by adding it to the `network.allow` list, but there is an important caveat.

For example, if `https://auth.example.com/**` represents the login page of an authentication provider and you add it to `network.allow`, access will fail if the provider's login page references resources from origins different from that URL unless all of those URLs are also added to the list.
However, it is not easy to identify every such URL in external content.

To mitigate this problem, you can use the `network.authorizedOrigin` list, which indicates whether specified origin servers can be trusted.
Only when a server listed here is treated as the origin are URLs not specified in `network.allow` also made accessible.

Example:

```json
{
  "network": {
    "allow": [
      "asset://main/**",
      "https://img.example.com/images/**"
    ],
    // Allow access to external sites when this server is the origin.
    "authorizedOrigin": [
      { "scheme": "https", "domain": "accounts.google.com" },
      { "scheme": "https", "domain": "login.live.com" },
    ]
  }
}
```

- Note that this is a form of privilege delegation, and servers added to this list are assumed to be trusted unconditionally.
  For example, if an asset on another server referenced by an external server specified in `authorizedOrigin` is compromised by a malicious third party, your app may be affected.
- It is also important that filters using `plugin.pages` and `plugin.mode` are configured correctly.
  Even if a page from an origin allowed here is loaded, only network access is allowed.
  If filtered by `plugin.pages`, it cannot access the muon plugin bridge.
  Also, because the default `plugin.mode` is `"validate"`, even an allowed page cannot call plugin functions without capability imports generated by the bundler.
  By default, `plugin.pages` references only local assets (`asset://main/**`), so the muon plugin bridge is not exposed to pages provided by external servers.
