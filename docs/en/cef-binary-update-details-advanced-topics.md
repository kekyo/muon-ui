# CEF binary update details (Advanced topics)

This information describes details of the CEF and Node.js runtime preparation process and is provided for analysis when problems occur.
Be careful: `muon-launcher.ini` is not intended to be configured manually.

## CEF version policy

The following values may be specified for `versionPolicy` in the `[cef]` section of `muon-launcher.ini`:

| Value | Behavior |
| :---- | :------- |
| `tested` | Uses the embedded CEF artifact verified when muon-core was built. This is the default. |
| `same-major-latest` | Uses the latest artifact from stable/minimal candidates with the same CEF major as `cefReference.version` and a matching CEF API hash. Falls back to `tested` if none is found. |
| `compat-latest` | Uses the latest artifact from all stable/minimal candidates with a matching CEF API hash. Falls back to `tested` if none is found. |
| `exact` | Uses the CEF version specified by `exactVersion`. A matching CEF API hash is required for versions different from `tested`. |

These policies and `exactVersion` apply only to CEF and do not affect Node.js version selection.

When embedding `muon.json` into an executable with `muon embed-config`, specify not only `muon-core` but also the final `muon-launcher` executable if you want `launcher.defaultVersionPolicy` to take effect at `muon-launcher` startup:

```bash
muon embed-config \
  --runtime-path ./dist/runtime/linux-amd64 \
  --launcher-path ./myapp \
  --config ./muon.json
```

## Catalogs, version selection, and caches

The CEF catalog is stored as `cef-catalog.json`, and the official Node.js release index is stored as `node-catalog.json`, directly under the muon cache.
`catalogRefreshIntervalSeconds` in `[runtime]` is the automatic refresh interval for catalogs applicable during each launch.
The default is 7 days (`604800`), and specifying `0` disables interval-based automatic refresh.
If a refresh fails while an existing catalog remains available, the existing catalog is used as a fallback.

For CEF, an artifact is selected from the official CEF catalog according to the policy.
For Node.js, muon considers releases in the official `https://nodejs.org/dist/index.json` that provide a file for the target platform and satisfy both the project's `package.json` `engines.node` range and the muon Node bridge compatibility range.
When `engines.node` is omitted, muon uses the latest compatible LTS release. If none matches, preparation fails without falling back to a non-LTS release.
When it is specified, muon prefers the greatest matching LTS version and otherwise uses the greatest matching version from all releases.

The cache layout is:

```text
<cache>/
+-- cef-catalog.json
+-- node-catalog.json
+-- node-checksums
|   +-- <version>
|       +-- SHASUMS256.txt
+-- artifacts
    +-- cef
    |   +-- <CEF archive>
    +-- node
        +-- <version>
            +-- <Node.js archive>
```

CEF archives are verified with the SHA1 and size supplied by the external CEF catalog.
For a Node.js archive, muon selects exactly one value for the target file name from the release's official `SHASUMS256.txt` and verifies the archive with SHA-256.
SHA-256 is also used for consistency verification of plugins, asset archives generated by muon, and launcher preparation state.

When both CEF and Node.js are required, the catalogs and archives applicable to each are prepared in parallel.
Calls from the parallel work into the progress callback are serialized.
If progress serialization is unavailable, preparation runs sequentially instead.

For tests and mirror operation, the `MUON_CEF_CATALOG_URL` environment variable can override the CEF catalog URL.
Artifact URLs are resolved relative to the same directory as the catalog URL.
For Node.js, `MUON_NODE_DIST_URL` can override the default `https://nodejs.org/dist`.
`index.json`, each version's `SHASUMS256.txt`, and archives are resolved from this URL.

## Launcher state and update requests

`muon-launcher.ini` has four sections:

```ini
[runtime]
catalogRefreshIntervalSeconds=604800

[cef]
versionPolicy=tested
lastCatalogUpdateUnix=0

[node]
lastCatalogUpdateUnix=0

[update]
requested=false
requestedAtUnix=0
```

`lastCatalogUpdateUnix` in `[cef]` and `[node]` is updated only when the corresponding catalog is actually replaced.
Calling `triggerUpdate()` from the launcher plugin saves `requested=true` in the shared `[update]` section, and applicable catalog refreshes are attempted the next time `muon-launcher` starts.
The Node.js catalog is not applicable to an app that does not require a Node.js runtime.
The request is reset to `requested=false` only when every applicable catalog is refreshed during that launch.
Falling back to an existing catalog does not count as a successful refresh, so the request remains set in that case.

## Publishing a runtime transaction

Runtime preparation places the source distribution and CEF into the runtime.
When Node.js is required, it installs only `runtimes/node/LICENSE` and `runtimes/node/bin/node` (`node.exe` on Windows) from the official archive.
npm, Corepack, and all other files in the Node.js archive are not installed.
When building `muon-core`, the same CEF preparer extracts the build CEF tree into `muon-core/.cef/`.

A prepared runtime has a `.muon-runtime-ready.json` file containing SHA-256 fingerprints corresponding to the source muon distribution, CEF, and the Node.js archive.
A sentinel of 64 zeroes is used for a component that does not apply, such as Node.js in an app that does not require it. In-place preparation of a portable distribution also uses this sentinel for the source muon fingerprint.
A runtime whose fingerprints match is reused.

When normal staging updates runtime contents, muon files, CEF, Node.js, `muon-launcher.ini`, and the ready marker are all written into a temporary directory, and the completed candidate is then published as the runtime directory. When the fingerprints match, the existing runtime is reused and only the launcher state is replaced atomically.
For in-place preparation of a portable distribution, the existing ready marker is invalidated before changes begin, and a new marker is published only after CEF and Node.js placement and launcher state persistence all succeed.
Consequently, a partially prepared runtime or a runtime whose state was published prematurely is not treated as ready.
