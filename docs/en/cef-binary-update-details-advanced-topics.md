# CEF binary update details (Advanced topics)

This information describes details of the CEF binary update process and is provided for analysis when problems occur.
Be careful: `muon-launcher.ini` is not intended to be configured manually.

The following values are specified for `versionPolicy` in `muon-launcher.ini`:

| Value | Behavior |
| :---- | :------- |
| `tested` | Uses the embedded CEF artifact verified when muon-core was built. This is the default. |
| `same-major-latest` | Uses the latest artifact from stable/minimal candidates with the same CEF major as `cefReference.version` and a matching CEF API hash. Falls back to `tested` if none is found. |
| `compat-latest` | Uses the latest artifact from all stable/minimal candidates with a matching CEF API hash. Falls back to `tested` if none is found. |
| `exact` | Uses the CEF version specified by `exactVersion`. A matching CEF API hash is required for versions different from `tested`. |

`catalogRefreshIntervalSeconds` is the automatic catalog refresh interval.
The default is 7 days (`604800`), and specifying `0` disables automatic updates.
Calling `triggerUpdate()` from the launcher plugin saves `requested=true`, and the catalog update is attempted the next time `muon-launcher` starts.
Only when the update succeeds is `requested` reset to `false`.

When embedding `muon.json` into an executable with `muon embed-config`, specify not only `muon-core` but also the final `muon-launcher` executable if you want `launcher.defaultVersionPolicy` to take effect at `muon-launcher` startup:

```bash
muon embed-config \
  --runtime-path ./dist/runtime/linux-amd64 \
  --launcher-path ./myapp \
  --config ./muon.json
```

This process has three major stages:

1. Download the CEF catalog according to the policy or update request and place it in `catalog.json`. If an existing catalog is present, its contents are used even if update fails.
2. Download the required CEF tarball into `artifacts/`. If it already exists, verify and use it with the SHA1 and size provided by the external CEF catalog.
3. During runtime preparation, copy the distribution source dist into the user state directory and then extract CEF into the same runtime directory. When building `muon-core`, use the same preparer to extract the build CEF tree into `muon-core/.cef/`.

The SHA1 used here matches the artifact verification value from the external CEF catalog.
SHA-256 is used for consistency verification of plugins, asset archives generated by muon, and launcher preparation state.

CEF binaries are selected by downloading the official catalog file and checking the required version.
For tests and mirror operation, the `MUON_CEF_CATALOG_URL` environment variable can override the catalog file URL.
Artifact URLs are resolved relative to the same directory as the catalog URL.
