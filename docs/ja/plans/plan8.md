# コア・利用者向け機能とバックエンドによるディレクトリ整理

## 目的と承認された方針

plan7までに実装したCEF・Androidの機能を維持し、当初の`muon-core`と`muon-ui`を軸とする構成を、両バックエンドに共通する配置へ整理する。`core`にはアプリ実行時の機能、`ui`には利用者向けのCLI、Vite連携、アプリのビルド・配布機能を置く。

バックエンドは当面CEFとAndroidの二種類を想定する。実装とテストは`cef`と`cef-test`、`android`と`android-test`のように同じ階層に置く。親の`test`ディレクトリの下へバックエンド別テストを集める構成にはしない。Linux・Windowsの区分はCEF側の内部に置く。ビルドツールが必要とする`src/main`などの配置は、そのコンポーネント内で維持する。

## 現在のコードで確認した境界

`muon-core`にはCEF固有のホストに加えて、Androidも使用するRPC、プラグイン実行、メタデータ、公開C APIがある。共有部分は`core/common`へ取り出し、AndroidからCEFの内部を参照する依存を解消する。共用テストプラグインと共有部分のテストは`core/common-test`へ置く。

`muon-android`にはJava・JNIのランタイム、WebViewへ注入するJS、Node.jsで動くアプリビルド機能が同居している。実行時のレンダラーとRPCクライアントは`core/android`へ置く。SDKの準備、Gradleプロジェクト生成、署名、利用者が指定するプラグインの入力検査は`ui/android`へ移す。実行時とビルド時の両方で使うAPI一覧や設定の定義は複製せず、一か所を参照する。

`muon-android-prototype`は現在も製品の端末テストとテストプラグインのビルドに使われている。QuickJSの試作も同じアプリへ組み込まれているため、製品の回帰テストを`core/android-test`へ、QuickJSの実装・検証アプリ・テストを`core/android-poc`へ分離する。試作機能は削除せず、既存の検証を維持する。

独立したnpm利用アプリのビルド・署名・更新の検証は`ui/android-test`へ置く。端末から対象アプリを操作するobserverは`core/android-test`が保持する。テストプラグインには明示的な成果物の出力先を設け、利用側がPoCアプリのGradle内部ディレクトリを参照する依存を解消する。

## 完成時の配置

```text
core/
  common/          共通RPC・プラグインランタイム・公開C API
  common-test/     共有機能のテスト・共用テストプラグイン
  cef/             CEFホスト・ブラウザ・デスクトップ機能
  cef-test/        CEF固有の単体テスト・結合テスト・E2E
  android/         Androidホスト・JNI・WebViewブリッジ
  android-test/    端末テスト・テストアプリ・observer
  android-poc/     QuickJSの試作とその検証
ui/
  package.json     公開npmパッケージmuon-ui
  common/          共通CLI・Vite連携・設定・ビルド制御
  common-test/
  cef/             CEF向け準備・ビルド・配布処理
  cef-test/
  android/         APKビルド・署名・プラグイン入力検査
  android-test/
builder/           現在のmuon-builder
node/              現在のmuon-node
deps/
scripts/
docs/
```

ディレクトリとnpm workspaceは一対一にしない。`ui`は一つの公開パッケージとしてまとめ、公開名は`muon-ui`を維持する。`muon-node`などの公開名、生成する実行ファイル名、アプリの公開APIも維持する。内部workspaceはビルドとテストの実行単位に合わせて設定する。

## 実装段階と各段階の完了条件

### 段階1：共有コアの独立

共有RPC、プラグイン実行、公開ヘッダーと必要な補助コードを`core/common`へ移す。共有機能のテストと共用プラグインを`core/common-test`へ移し、CEFとAndroidのビルド定義から参照する。CEF不要で動く既存のテストを、新しい配置からビルド・実行できるようにする。

移動先を使う既存の振る舞いテストで未接続の状態を確認した後、参照とビルドを接続する。ファイル名やソース文字列の一致だけを検証するテストは追加しない。共有テストが成功し、CEF・Androidの既存ビルドから共有部分を利用できることを完了条件とする。

### 段階2：コンポーネントの移動

CEF本体を`core/cef`へ、CEFの単体テストと`muon-core-tester`を`core/cef-test`へ移す。Androidを`core/android`、現行テストホストを`core/android-test`、`muon-ui`を`ui`、`muon-builder`を`builder`、`muon-node`を`node`へ移す。この段階ではAndroidの試作分離とui内部の責任別分割は次段階へ残し、移動後の構成を動作可能にする。

workspace、import、CMake・Gradle・Makefile、シェルスクリプト、Vite・Vitest、IDE設定、CIの参照を更新する。古いビルドキャッシュに含まれる絶対パスを持ち越さず、必要な生成物を新しい場所で作り直す。バックエンドのビルドと関連する既存テストが、新しい配置から成功することを完了条件とする。

### 段階3：Androidの製品検証と試作の分離

製品のテストホストをQuickJSなしで動かし、WebView・RPC・プラグイン・fullscreen・資源解放の検証を維持する。QuickJSのJava・JNI・JS・アセットと固有テストを`core/android-poc`へ移し、専用の実行単位で検証する。共通ランタイムを複製せず、両ホストから同じ実装を参照する。

observerを`core/android-test`へ移す。Android用テストプラグインのビルド定義と成果物の出力先を整理し、利用アプリの検証がその成果物を明示的に利用するようにする。QuickJSなしの製品テストアプリとQuickJS試作アプリがそれぞれビルドでき、関連テストが成功することを完了条件とする。

### 段階4：uiの責任別分割

共通のCLI・Vite連携・設定・ビルド制御、CEF固有処理、Android固有処理を、それぞれ`ui/common`、`ui/cef`、`ui/android`へ配置する。Androidのホスト側ビルド処理と利用アプリ生成テンプレートをui側へ移す。テストも対象に合わせて兄弟ディレクトリへ分ける。

公開エントリーポイント、型定義、ESM/CJS出力、CLI、Vite連携と配布物へのランタイム同梱を接続する。単純な移動で済まない混在ファイルは、バックエンド固有部分を切り出して既存の振る舞いを維持する。各領域の既存テスト、パッケージのビルドと読込みが成功し、公開パッケージから両バックエンドを使用できることを完了条件とする。

### 段階5：参照・文書の仕上げと全体検証

利用者向け文書、既存計画書のローカルリンク、ビルド・配布スクリプト、CI、IDE設定を完成時の配置に合わせる。過去の実施記録の内容は維持し、現在のファイルへの参照を更新する。日本語文書を原本として必要な英語文書も更新する。

ルートの全体テストを最後まで実行する。Androidは利用できる実機・エミュレーターで、plan7のsimple・validate、両ABI、release更新、fullscreenの表示・復帰と動画、QuickJS試作の検証を行う。環境不足がある場合は具体的な不足を報告し、必要な導入を促す。既存生成物に依存する参照が残らず、外部依存コードを変更していないことも確認する。

## 作業方法と対象外

各段階で実行できる成果物を残し、問題の再現、修正、検証を行ってから`refactor:`または`fix:`でコミットする。計画保存と文書整理は`doc:`、ビルド設定などは必要に応じて`chore:`を使う。mainへはマージしない。

機能追加、公開APIの変更、QuickJSの製品化、外部依存コードの変更、テスト範囲の縮小は行わない。分割に必要な参照・ビルド・テストの調整を対象とする。新しい問題が見つかった場合は配置や依存方向の判断を見直し、場当たり的な互換パスや旧ディレクトリへのリンクで隠さない。

## 最終完了条件

- 承認された`core`・`ui`とバックエンド別の配置になっている。
- 共有コアをCEF・Androidの両方が使用し、AndroidからCEF固有コードを参照していない。
- 製品のAndroidテストとQuickJS試作が独立して動作する。
- 公開npmパッケージ、CLI、型定義、両バックエンドのビルドと配布経路が維持されている。
- 旧PoCのビルド中間ファイルへ依存せず、テストプラグインを再生成して検証できる。
- 全体テストと実行可能な端末検証を完了し、結果と環境上の制約を本計画へ記録している。
- 段階ごとのコミットがあり、mainへのマージと外部依存コードの変更がない。
