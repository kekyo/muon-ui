# Constraints

## Wayland and Vulkan

The current CEF (`147.0.14+g76d2442`) does not fully support use with Vulkan in Linux + Wayland environments.
This combination reportedly causes problems in many cases, so muon automatically disables CEF Vulkan-related features when the Linux display backend is determined to be Wayland.
For example, this applies when `XDG_SESSION_TYPE=wayland`, `WAYLAND_DISPLAY`, or `--ozone-platform=wayland` is detected.
On the other hand, when an X11 backend is explicitly specified, such as `--ozone-platform=x11`, this disabling is not performed.

Also, in Wayland environments where the GL/ANGLE backend is not explicitly specified, muon adjusts CEF to use ANGLE's OpenGL backend to avoid ANGLE through Vulkan.

## Filter feature for virtual module imports

Note that the filter feature for muon plugin virtual module imports does not completely eliminate supply-chain attacks.
When a request is made to muon code at runtime, it filters function calls by using a random capability ID generated by Vite.
This ID is difficult to guess, but if it is identified through dynamic analysis of the loaded bundle or by malicious code running on the same page, the filter may be bypassed.

On the other hand, page URL filters, which are automatically configured in `validate` mode and manually configured in `simple` mode, are stronger because they prevent JavaScript from referencing the muon object itself.
Therefore, always take care not to expose unnecessary plugin functions.

## Android WebView backend

See [building and distributing Android apps](./android.md) for public APK commands and verified environments. FCM and QuickJS are unavailable in public application builds. QuickJS mentioned below applies only to the prototype host.

The Android WebView backend does not comprehensively intercept normal WebView network traffic through muon. CEF settings such as `network.allow`, `network.authorizedOrigin`, and `network.localAccess` may remain in a shared `muon.json`, but Android does not enforce them as allow or deny rules for WebView traffic and emits a warning when they are explicitly configured.

On Android, the Manifest `INTERNET` permission, local-network permissions required by the device and API level, and Network Security Config act as application-wide boundaries outside muon. Web-platform restrictions such as CORS and CSP also apply normally. In an environment with `INTERNET` permission, assume that WebView can communicate externally without a muon destination allowlist.

Muon plugin RPC is accepted only from the trusted HTTPS asset origin's main frame. Direct RPC from foreign main frames, foreign iframes, and same-origin iframes is rejected. This does not guarantee isolation from a same-origin iframe accessing the parent page. JavaScript files sharing a page are not authenticated individually at runtime. Simple mode exposes the configured API; validate mode permits calls within the scope of an obtained valid capability. Use CSP and dependency controls as well. See [WebMessageListener source metadata](https://developer.android.com/reference/androidx/webkit/WebViewCompat.WebMessageListener).

Validate mode checks direct imports through Vite's `sources` and `packages` rules. The native host checks capability IDs and function permissions. `plugin.pages` supports omission, an empty list, `asset://main/**`, and `https://main.asset.muon.invalid/**`; other conditions fail at build time. An empty list disables the bridge. Origin rules do not filter full URLs including paths, so Android does not provide full compatibility with CEF page URL globs. See [WebViewCompat injection rules](https://developer.android.com/reference/androidx/webkit/WebViewCompat).

Public APK builds use the fixed asset origin `https://main.asset.muon.invalid`. Muon handles this host locally, including missing assets, without forwarding requests to the network. Multiple asset hosts and custom host names are unsupported in public builds. The [network-filter validation record](../../filter-limitation.md) describes earlier configuration proposals and findings.

The current Android `muon.fs` handles real filesystem paths allowed by Android. Direct `content://` URI access and `muon.fs.dialogs` are unsupported. `muon.launcher`, `muon.executor`, and the desktop Node.js sidecar are unavailable. External native plugins packaged inside the APK work in simple and validate modes; adding plugins from outside the APK after installation is unsupported. See [native plugin configuration](./android.md#prebuilt-native-plugins).

In the Android prototype host, `muon.node.createNode()` creates an embedded QuickJS runtime in a separate-process Service and provides a limited set of Node-like modules. It is not compatible with Node.js, npm packages, CommonJS, or the complete standard library. See the [Android API compatibility policy](../../android-api-compatibility.md) for supported functions and the [Android prototype host](../../muon-android-prototype/README.md) for QuickJS modules, network boundaries, and resource limits.

## Limitations on enabling the CEF sandbox on Linux

On Linux, when a muon app is not started with administrator privileges, the `cef-sandbox` required by CEF cannot be started correctly.
This occurs when build artifact files output under `dist-muon/` are launched directly with user privileges.
To launch correctly, either start with administrator privileges or install the `deb` package through APT so that `cef-sandbox` can be started with administrator privileges.
